# Feature: Fix Done-state post-save cleanup failure retryability (FR-PRD-WAITING-POSTSAVE-001)

## Description
When `do_approval_transition` successfully saves `Done` state but subsequently fails to remove `ralph:prd-active`, the issue becomes permanently terminal with stale labels (`ralph:prd-active` and `ralph:waiting-feedback`). This happens because: (1) `finish_transition` captures `pre_transition_state` after `do_approval_transition` has already mutated `state.state` to `Done`, so the "revert" is a no-op; (2) on the next tick, `advance_issue` sees `is_terminal() == true` and skips all transition logic, so cleanup is never retried. This feature makes post-save `Done` cleanup failures retryable and ensures both label removals are attempted regardless of individual failures.

## Acceptance Criteria
- [ ] In `do_approval_transition`, post-save `ralph:prd-active` removal failure does not short-circuit before `ralph:waiting-feedback` removal — both removals are attempted independently.
- [ ] When post-save label cleanup fails in `do_approval_transition`, the in-memory state is reverted from `Done` to `AwaitingFeedback` before returning the error, so `finish_transition` sees a non-terminal state and retry accounting works correctly.
- [ ] On next tick after a cleanup failure, the issue is not skipped by `advance_issue`'s terminal check — it re-enters the `AwaitingFeedback` transition and can reattempt approval and cleanup.
- [ ] The `transition_to_failed` path is unaffected (it already uses `let _ =` for all post-save removals and is correctly non-short-circuiting).
- [ ] Integration test covers "Done save succeeds, `--remove-label ralph:prd-active` fails" scenario: state remains non-terminal, next tick retries cleanup.
- [ ] Conformance test covers the same failure scenario.
- [ ] All existing tests continue to pass (`cargo test`, `nix build -L`, `ralph validate`).

## Files to Modify/Create
- `src/daemon/interactive_prd.rs` — Three changes in `do_approval_transition` (lines 1484–1527):
  1. After the successful save at line 1494, change the `ralph:prd-active` removal from fallible `?` to best-effort `let _ =`, collecting whether it succeeded.
  2. Always attempt `ralph:waiting-feedback` removal (already `let _ =`) regardless of active-label result.
  3. After both removals, if the active-label removal failed, revert `state.state` from `Done` back to `AwaitingFeedback` and return an error so retry accounting kicks in. This ensures the on-disk state is `Done` but in-memory state is reverted, and `finish_transition` will re-save with the non-terminal state (overwriting the `Done` save), keeping the issue retryable.
  
  Alternative approach (simpler): Instead of reverting after both removals, make both removals best-effort (`let _ =`) and return `Ok(())`. This treats label cleanup as non-critical — the issue is terminally `Done` and stale labels are cosmetic artifacts. This matches the existing `transition_to_failed` pattern where all post-save removals are `let _ =`. However, this approach may not satisfy the amendment's requirement for retryability.

  Recommended approach: Collect cleanup errors, attempt both removals, then if either failed, revert the on-disk state by re-saving with `AwaitingFeedback` before returning the error.
