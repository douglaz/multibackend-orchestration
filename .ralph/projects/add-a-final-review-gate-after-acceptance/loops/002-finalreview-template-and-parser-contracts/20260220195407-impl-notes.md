# Implementation Notes

## Decisions Made
- Template functions follow the existing naming convention: `default_{role}_template()` returning `&'static str` with embedded markdown
- Template path defaults follow the pattern `templates/{role}.md` matching the existing convention (e.g. `templates/final_reviewer.md`)
- Parser types use separate structs per role (FinalReviewerDecision, PlannerPositionsDecision, VoteDecision, ArbiterDecision) rather than a generic enum, to keep type safety and match existing parser patterns
- Amendment extraction uses `## Amendment: {ID}` H2 headings as block delimiters, with `### {ValueSection}` (Position/Vote/Ruling) as the per-amendment value indicator
- `validate_exact_id_coverage` checks both missing and extra IDs bidirectionally, ensuring strict coverage
- `validate_accept_reject` validates that values are exactly `ACCEPT` or `REJECT` (case-sensitive, matching template instructions)
- Planner prompt amendment injection reads `final-review-amendments-applied.md` from `project_dir` (not a loop subdirectory) and uses `append_section_if_missing` with alias key `final_review_amendments` under heading `## Final Review Amendments`
- Config CLI `set_backend_model` and `set_role_timeout` were extended to recognize `final_reviewer`, `arbiter`, and `acceptance_qa` roles that were previously missing from the CLI setter (but present in the data model)

## Spec Deviations
- The spec mentions adding final_review template path tests in `src/config/global.rs` — these were added inline in the existing `default_workspace_tmux_settings_match_expected_values` test which already checks all template defaults, rather than creating a separate test function
- The spec lists `src/validate/tests_final_review.rs` as a new file to create — this is out of scope for this loop's acceptance criteria (which focuses on templates, parsers, config, and init). The validate tests for the full final-review flow will be added when the orchestrator flow is implemented
