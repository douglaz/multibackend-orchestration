# Feature: Oracle Review Comment Post/Readback Failure Separation

## Description
The oracle review phase currently treats comment readback failures identically to actual post failures. When `post_bot_comment_with_marker_with_gh_bin` returns `Err`, the phase does not distinguish between "the `gh issue comment` command failed" and "the comment was posted but the subsequent `gh issue view --json comments` readback failed." This means a successful post followed by a transient readback failure causes the daemon to not save state and not count toward the per-cycle cap, allowing more reviews than configured and forcing unnecessary self-healing on the next cycle.

This feature implements amendment ORACLE-REVIEW-FR-001 from the Round 2 final review by splitting the post operation into distinct outcomes and ensuring state advances whenever a comment is actually posted to GitHub.

## Acceptance Criteria
- [ ] `post_bot_comment_with_marker_with_gh_bin` (or a new wrapper/return type) distinguishes three outcomes: `already_exists`, `posted`, and `post_failed`
- [ ] A zero-exit `gh issue comment` is treated as `posted` even if the optional readback of comment metadata fails afterward
- [ ] In `oracle_review_phase`, state is advanced and `success_count` incremented on `posted` (not only on successful readback)
- [ ] `already_exists` does not count toward `success_count` (existing behavior preserved)
- [ ] `post_failed` does not advance state (existing behavior preserved)
- [ ] A new validate conformance test covers the scenario where `gh issue comment` succeeds but `gh issue view --json comments` readback fails, asserting that state advances and per-cycle cap reflects the posted review
- [ ] Existing tests continue to pass without behavioral changes
- [ ] No changes to `pr_review_phase` or any other consumer of the posting helper—only the oracle review phase changes its success boundary

## Files to Modify/Create
- `src/daemon/github.rs` — Introduce a `PostCommentOutcome` enum (or similar) with variants `AlreadyExists(IssueComment)`, `Posted`, and a clear separation of post-vs-readback errors. Modify `post_bot_comment_with_marker_with_gh_bin` (or add a sibling function) so that a successful `gh issue comment` exit code is reported as success even if the readback call fails (readback failure can be logged as a warning inside the helper). Existing callers that use the current `Result<Option<IssueComment>>` must not break.
- `src/daemon/oracle_review.rs` — Update the match on the post result (around line 229) to use the new outcome type. Advance state and increment `success_count` on `Posted`. Keep `AlreadyExists` as a skip (no count increment). Keep genuine post failures as warnings that do not advance state.
- `src/validate/tests_daemon_oracle_review.rs` — Add a conformance test `comment_readback_failure_still_advances_state` that configures the mock so `gh issue comment` succeeds but the subsequent `gh issue view --json comments` call fails, then asserts: (1) state is persisted for that PR/SHA, (2) `success_count` reflects the posted review toward the per-cycle cap, (3) other eligible PRs are still processed.
