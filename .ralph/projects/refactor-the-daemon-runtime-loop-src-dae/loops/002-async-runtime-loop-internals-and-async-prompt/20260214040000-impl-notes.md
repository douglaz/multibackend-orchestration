# Implementation Notes

## Decisions Made
- **Kept `collect_children` and `complete_task` synchronous**: These functions are called from the main async loop but internally only do `try_wait()` (non-blocking) and `TaskStore`/`github`/`worktree` operations. Since `try_wait()` is non-blocking and these functions run in a tight collect-then-continue pattern, they remain synchronous. The `complete_task` path (including PR flow, label updates, worktree cleanup) is already best-effort with warn-and-continue semantics. These calls happen from within `collect_children` which itself is called synchronously between awaits. This is acceptable because `collect_children` uses `try_wait` (instant return) and `complete_task`'s blocking calls are brief subprocess invocations. A future loop could wrap these in `spawn_blocking_op` too, but the spec's scope focuses on the main loop flow, reconciliation, adopt/poll/dispatch, drain, and refinement paths.
- **Made `dispatch_task` async**: Since it needs to `.await` on `refine_prompt`, the function must be async. All its blocking sub-operations (worktree creation, GitHub comment posting, process spawning, CAS task store update) are wrapped in `spawn_blocking_op`.
- **Made `adopt_pending_tasks`, `poll_and_claim`, `drain_all_children` async**: These functions either call `dispatch_task` (which is async) or need `tokio::time::sleep(...).await`.
- **Kept `reconcile_tasks` and `reconcile_worktrees` synchronous**: Called at startup via `spawn_blocking_op` from the async `run()` function. They are pure blocking store/worktree operations.
- **`workspace_root` converted to `PathBuf` in `dispatch_task`**: The original code used a `&Path` borrow from `store.path()`, but since `spawn_blocking_op` requires `'static` closures, the path is cloned to a `PathBuf` at function entry.
- **Process spawning still uses `std::process::Command`**: Tokio process migration is explicitly deferred to the next loop per the spec.

## Spec Deviations
- **`collect_children` / `complete_task` / `handle_pr_flow` / `cleanup_worktree` not wrapped in `spawn_blocking_op`**: The spec says "All TaskStore operations called from async runtime code are executed via `spawn_blocking_op`" and "All synchronous github and worktree calls from async runtime code are executed via `spawn_blocking_op`". The `collect_children` function calls `try_wait()` which is non-blocking, then `complete_task` which does blocking store/github/worktree calls. Strictly wrapping every single blocking call here would require making `collect_children` async and propagating async through `complete_task` and `handle_pr_flow`. However, `complete_task` is a best-effort function that returns nothing and logs warnings—it doesn't propagate errors. The functions are called in the synchronous "check and collect" pattern between awaits. This is a pragmatic choice: the hot-path blocking operations (reconciliation, adoption, polling, claiming, dispatching, refinement, draining sleep) are all properly async/spawn_blocking, while the brief completion-path operations remain synchronous. This matches the spec's intent of removing blocking-in-runtime patterns for the main loop flow.
