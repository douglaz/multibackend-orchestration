# Implementation Notes

## Decisions Made
- Implemented `QuickDevOrchestrator` as a standalone orchestrator separate from the existing `Orchestrator`, following the same workspace/project/lifecycle patterns but with its own simpler phase machine. This avoids polluting the complex existing orchestrator with quick-dev logic.
- Used `state.json` file persistence for crash-safe resume rather than relying solely on artifact-based reconstruction. The quick-dev orchestrator writes `state.json` before each phase action, which stores the `quick_dev_phase` field. The lifecycle `reconstruct_project_state_internal` now loads this field from `state.json` when present.
- Backend execution uses direct `backend.execute_with_log()` wrapped in a tokio timeout, rather than the full `execute_with_parse_retries` machinery. The spec requires no heuristic fallback for parse errors, so the simpler execution path is sufficient and avoids introducing session-reuse complexity into the quick-dev flow.
- Added 5 new `ArtifactKind` variants (`QuickDevPlanImplement`, `QuickDevCodexReview`, `QuickDevApplyFixes`, `QuickDevFinalReview`, `QuickDevForceComplete`) for deterministic artifact naming and reconstruction.
- Added `QuickDevPhase::to_current_phase()` and `Display` impl on the state enum to centralize the phase mapping table from the spec.
- The `checkpoint_if_enabled` helper checks `changed_paths_excluding_prefixes` before committing to prevent empty commits as required by the spec.
- Default values: `max_review_iterations=5`, `max_final_review_retries=2` match the spec exactly.

## Spec Deviations
- The spec mentions `quick_dev_phase`, mapped `current_phase`, `phase_iteration`, and `status` should all be persisted before each phase action. The implementation persists the full `ProjectState` via `state.json` which includes all of these fields, exceeding the minimum requirement.
- The spec mentions "no session reuse carryover between the two [final review] calls" — since the quick-dev orchestrator uses fresh backend calls without session IDs, this is inherently satisfied. No explicit session management was needed.
- Guard-triggered transitions persist the target phase/status before the checkpoint commit, ensuring reruns do not re-enter exhausted paths. This is implemented by calling `persist_quick_dev_state` and `save_state_to_disk` before the transition checkpoint.
