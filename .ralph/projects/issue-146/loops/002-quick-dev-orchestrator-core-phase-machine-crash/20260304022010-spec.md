# Feature: Quick-Dev Orchestrator Core (Phase Machine + Crash-Safe Resume)

## Description
Loop 1 already completed the quick-dev foundation (`QuickDevPhase` type, strict parser contracts, template/config plumbing, and prompt builders). The next missing feature is the executable quick-dev engine: implement the 4-phase `QuickDevOrchestrator` with durable phase persistence, strict backend-role resolution, review/final-review guard behavior, and git checkpoint transitions. This loop should deliver the internal runtime core that later CLI/daemon wiring can call.

## Acceptance Criteria
- [ ] Add `QuickDevOrchestrator` in `src/workflow/quick_dev_orchestrator.rs` with `run(&mut self, options) -> Result<OrchestrationResult>`.
- [ ] Add `QuickDevRunOptions` with `project`, `implementer_backend`, `reviewer_backend`, `pr_url`, `skip_commit`, `max_review_iterations`, and `max_final_review_retries`.
- [ ] Default `max_review_iterations` to `5` and `max_final_review_retries` to `2` when not explicitly set.
- [ ] Backend resolution follows required precedence: implementer = CLI override -> effective `implementer_backend` -> effective `starting_backend`; reviewer = CLI override -> effective `reviewer_backend`.
- [ ] If reviewer backend is missing/unresolvable, fail fast with exact message: `"quick-dev requires a second backend for review"`.
- [ ] If implementer and reviewer backend specs resolve to the same value, fail fast with a clear validation error (no single-backend fallback).
- [ ] Resume source is persisted `quick_dev_phase`; if `None`, execution starts at `PlanAndImplement`.
- [ ] Persist quick-dev state before each phase action (`quick_dev_phase`, mapped `current_phase`, `phase_iteration`, and `status`).
- [ ] `phase_iteration` semantics match spec: `1` on `PlanAndImplement`/`CodexReview`/`FinalReview`; `ApplyFixes` uses current review-loop iteration (1-based, incrementing each re-entry).
- [ ] Implement exact phase transitions: `PlanAndImplement -> CodexReview`; `CodexReview -> FinalReview` on `ReviewSatisfied`; `CodexReview -> ApplyFixes` on `ChangesRequested`; `ApplyFixes -> CodexReview`; `FinalReview -> PlanAndImplement` on issues; `FinalReview -> Completed` on dual-complete.
- [ ] `CodexReview` output is parsed only with `parse_codex_review_output`; no heuristic fallback.
- [ ] Final review performs exactly two sequential calls (implementer then reviewer), each parsed with `parse_quick_final_review_output`.
- [ ] Final review calls must use fresh context (no session reuse carryover between the two calls).
- [ ] `max_review_iterations` guard: when reached, skip to `FinalReview` and emit a warning artifact/log.
- [ ] `max_final_review_retries` guard: when reached, write a force-complete artifact and mark project `Completed`.
- [ ] Quick-dev orchestrator never calls `github::mark_pr_ready()` and does not import daemon PR lifecycle helpers.
- [ ] Git checkpoint transitions use public `git/commit.rs` APIs directly and apply guard logic: skip when auto-commit disabled, `skip_commit` true, or not a git repo.
- [ ] No empty transition commits are created (skip checkpoint commit when only orchestration/runtime state changed).
- [ ] Failure invariant: if backend call, parse, or artifact write fails inside a phase, persisted state remains at that phase (`quick_dev_phase` + mapped `current_phase` consistent), `status` remains `InProgress`, and rerun resumes from that same phase.
- [ ] Failure invariant: guard-triggered transitions (`max_review_iterations`, `max_final_review_retries`) persist target phase/status before exit so reruns do not re-enter exhausted paths.
- [ ] Add unit/integration tests for happy path, review loop, final-review reloop, both guards, resume from `None`/`CodexReview`/`FinalReview`, missing reviewer backend, equal backend rejection, and commit-guard behavior.
