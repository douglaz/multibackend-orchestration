# Feature: Per-Role Backend/Model Overrides

## Description
Allow users to specify which backend (and optionally which model) to use for each orchestration role (planner, implementer, reviewer, completer) independently via CLI flags, project config, or global config. When a per-role override is set, it bypasses the normal alternation logic for that role. Roles without overrides continue to use the default alternation behavior.

This encompasses: adding the four new optional fields to all three config layers (`WorkflowConfig`, `ProjectWorkflowOverrides`, `EffectiveWorkflowConfig`), adding four CLI flags to `RunArgs`, updating config resolution and validation, modifying `assign_feature_backends()` and `assign_completion_backends()` to accept and apply role overrides, wiring the overrides through the orchestrator, and ensuring health checks cover override backends.

## Acceptance Criteria
- [ ] Four new optional fields (`planner_backend`, `implementer_backend`, `reviewer_backend`, `completer_backend`) added to `WorkflowConfig` in `src/config/global.rs` with `#[serde(default)]`
- [ ] Same four optional fields added to `ProjectWorkflowOverrides` in `src/config/project.rs`
- [ ] Same four optional fields added to `EffectiveWorkflowConfig` in `src/config/mod.rs` as `Option<String>`
- [ ] Config resolution in `resolve_effective_config()` applies CLI > project > global > None precedence for each per-role field
- [ ] Each per-role override is validated using `parse_backend_spec()` + known backend check (same pattern as `starting_backend` validation)
- [ ] Four new CLI flags added to `RunArgs`: `--planner-backend`, `--implementer-backend`, `--reviewer-backend`, `--completer-backend` (all `Option<String>`)
- [ ] A `RoleOverrides` struct (or equivalent) is added to `src/backend/mod.rs` with four `Option<String>` fields
- [ ] `assign_feature_backends()` signature updated to accept role overrides; uses override for planner/implementer/reviewer when set, falls back to alternation when not
- [ ] `assign_completion_backends()` signature updated to accept role overrides; uses override for planner/completer when set, falls back to alternation when not
- [ ] Orchestrator in `src/workflow/orchestrator.rs` constructs `RoleOverrides` from `EffectiveWorkflowConfig` and passes them to both `assign_feature_backends()` and `assign_completion_backends()`
- [ ] Health checks include per-role override backends (call `get_or_create_for_spec()` for each override during startup)
- [ ] Bare names like `"claude"` and spec strings like `"claude(sonnet)"` both work as overrides
- [ ] Roles without overrides continue to alternate normally (existing alternation logic preserved)
- [ ] State.json records the actual backend used (override or alternation result) — no changes needed, existing `FeatureLoopBackends`/`CompletionLoopBackends` structs handle this
- [ ] All existing tests continue to pass
- [ ] Unit tests for `assign_feature_backends` with various override combinations (all overrides set, partial overrides, no overrides)
- [ ] Unit tests for `assign_completion_backends` with override combinations
- [ ] Unit tests for config resolution with per-role overrides at different precedence levels
