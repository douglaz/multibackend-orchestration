# QA: FAIL

## Summary

The core daemon `--data-dir` provisioning and multi-repo runtime fan-out implementation is functionally correct. Manual end-to-end testing confirms all primary behaviors work: clone/bootstrap, guard rejection, duplicate repo detection, multi-repo status aggregation, cross-repo abort with ambiguity detection, and single-iteration mode. However, **5 conformance tests fail in `nix build`** due to three distinct bugs.

## Failures

### FAIL-1: `daemon_start_rejects_git_data_dir` — preflight ordering

**File:** `src/cli/daemon.rs:94-97`

`preflight_check_gh()` (line 94) runs before `guard_not_git_repo()` (line 97). In environments where `gh` is not on PATH (including the nix build sandbox), the test gets error `gh (GitHub CLI) not found in PATH` instead of the expected `must not be inside a git repository`.

**Evidence:** The test at `src/validate/tests_daemon.rs:6881` does not mock `gh` because it expects to fail at the guard check before needing gh. But the guard never runs.

**Fix:** Swap lines 94 and 97 so `guard_not_git_repo()` runs before `preflight_check_gh()`.

### FAIL-2: Three rebase tests — mock git breaks `guard_not_git_repo()`

**Tests:**
- `daemon::rebase_pr_comment_not_issue` (line 6230)
- `daemon::rebase_dedup_by_head_sha` (line 6317)
- `daemon::rebase_force_with_lease_rejection` (line 6424)

**File:** `src/validate/mock_scripts.rs:938-950`

These tests prepend a mock `git` to PATH that handles `rev-parse --show-toplevel` by printing `pwd` and exiting 0. When `execute_start()` calls `guard_not_git_repo()`, it picks up the mock git instead of the real one and concludes the data-dir is inside a git repo, causing `--data-dir must not be inside a git repository`.

**Evidence:** Mock git script at lines 938-950 unconditionally succeeds for `rev-parse --show-toplevel`. The guard at `src/cli/daemon.rs:326-343` runs `git rev-parse --show-toplevel` using whatever `git` is in PATH.

**Fix options:**
1. Add a `rev-parse --show-toplevel` handler to the mock git that checks for an env var like `RALPH_SKIP_GIT_GUARD=1` and exits non-zero to simulate "not a git repo".
2. Have `guard_not_git_repo()` use a hard-coded path to real git (e.g., `/usr/bin/git` or resolve from an env var like `RALPH_REAL_GIT`).
3. Make the mock git `rev-parse --show-toplevel` handler return non-zero when the CWD is the data-dir (not a repo working tree).

### FAIL-3: `config_merge_and_defaults` — project config not loaded for different repo slug

**File:** `src/validate/tests_daemon.rs` (the `config_merge_and_defaults` test)

The test creates a `new_daemon` harness at `acme/widgets` and writes project config there (poll=15s, max_concurrent=3, labels=ralph:ready,priority:high), but then runs `daemon start --repo acme/project-override`. The new clone-based provisioning creates a fresh repo for `acme/project-override` which has no project config, so defaults apply (poll=60s, max_concurrent=5, labels=ralph:ready).

**Evidence:** The test's assertion expects per-project override values, but those overrides only exist in the `acme/widgets` harness directory, not in the freshly cloned `acme/project-override`.

**Fix:** The test needs to either:
1. Use the same repo slug that has the config (`acme/widgets`), or
2. Set up the config in a way that the clone target will contain it (mock gh clone that copies config), or
3. Use workspace-level config (ralph.toml) instead of project-level config, since workspace config is written into the repo that gets cloned.

## Verdict

The implementation is **functionally sound** for all new behaviors. The 5 conformance test failures are caused by **test-environment interaction bugs**, not fundamental logic errors:

1. **FAIL-1** is a one-line ordering fix.
2. **FAIL-2** is a mock script limitation that needs the mock git to cooperate with `guard_not_git_repo()`.
3. **FAIL-3** is a test setup issue where project config is written to the wrong repo directory.

All three are fixable without changing the core daemon logic.
