This is a significant concern. The `inject_daemon_data_dir_arg` function will auto-inject `--data-dir` into all these calls. For example, `h.ralph(["daemon", "status"])` will become `h.ralph(["daemon", "status", "--data-dir", "<temp_dir_path>"])`. Since `--data-dir` is now required for `status`, this auto-injection actually helps these tests compile/run with the new CLI shape.

But the tests that call `h.ralph(["daemon", "start", "--repo", ...])` will also get `--data-dir` injected, pointing to a non-git-repo directory. The `start_validates_inputs_and_workspace` test at line 746 calls `h.ralph(["daemon", "start", "--repo", "acme/widgets", "--single-iteration"])` — which will get `--data-dir` injected. But `execute_start` still calls `Workspace::discover()`, which depends on `cwd` being inside a `.ralph/` workspace. The test runs from `repo_root` (via `current_dir(&self.repo_root)` in `ralph()`), not from `data_dir`.

This is actually fine for this scoped feature — `execute_start` still uses `Workspace::discover()` which is cwd-based, and `ralph()` sets `current_dir` to `repo_root`. The `data_dir` is accepted as an arg but ignored (`let _ = &args.data_dir;` essentially). The auto-injection is forward-looking infrastructure.

However, this auto-injection pattern is concerning from a code quality standpoint: it modifies ALL method calls (including `ralph()`, `ralph_with_stdin()`, `ralph_env()`) not just daemon-specific ones. The function is smart enough to only inject when `args[0] == "daemon"`, so it's safe, but it adds hidden implicit behavior to the test harness.

## Notes

**Harness `prepare_cli_args` / `inject_daemon_data_dir_arg`**: The implementation adds auto-injection of `--data-dir` into *all* harness methods (`ralph()`, `ralph_with_stdin()`, `ralph_env()`), not just `daemon_env()`. This is forward-looking infrastructure that will prevent every existing daemon conformance test from needing manual `--data-dir` additions. The injection function is guarded correctly — it only fires when `args[0] == "daemon"` and the subcommand is `start`/`status`/`abort`, and it skips injection if `--data-dir` is already present. This is a pragmatic choice that eliminates a large mechanical migration burden, though it adds implicit behavior to the harness.

**`resolve_repo_from_gh()` removed, `resolve_git_root()` retained**: The spec calls for removing `resolve_repo_from_gh()` (done) and retaining `resolve_git_root()` until the full `execute_start` rewrite. This is correct — `resolve_git_root` is still called at `daemon.rs:131`.

**Spec deviation acknowledged**: `execute_start` still runs a single repo (the first normalized one) rather than multi-repo JoinSet. The impl-notes explicitly document this as deferred to a later feature, which is consistent with the feature spec's "minimal behavioral changes" scope.

**`name.contains('/')` check in `validate_repo_slug`**: Technically redundant since `split_once('/')` already captures only up to the first `/`, and `is_valid_repo_component` would reject `/` anyway. Not a defect — defense-in-depth.
