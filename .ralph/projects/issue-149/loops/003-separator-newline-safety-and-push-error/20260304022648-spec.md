# Feature: Separator Newline Safety and Push-Error Classification Hardening

## Description
Address two edge-case gaps identified during completion review of the daemon resilience hardening (Loop 1):

1. **Separator newline safety**: The retrigger separator in `open_log_file_append()` writes `\n--- retrigger at <ts> ---\n\n`, which only produces a blank line before the separator if the existing log content already ends with a newline. If the prior log output lacks a trailing newline, the separator appears immediately after the last content character with no blank line preceding it, violating the spec requirement "with blank lines around it." Fix: read the last byte of existing content and emit an extra `\n` when the file does not end with a newline.

2. **Push-error classification tightening**: `is_retryable_push_error()` defaults unknown errors to retryable (`true`). While the existing non-retryable patterns (`"denied"`, `"forbidden"`, etc.) catch most permanent failures, an explicit `"403"` pattern is missing (a bare `HTTP 403` without the word "Forbidden" would be retried), and the test suite only covers four error messages. Add the `"403"` non-retryable pattern and expand test coverage to include the full set of prompt-specified examples (policy rejection containing "GH013", HTTP 403, protected-branch hook rejection).

## Acceptance Criteria
- [ ] `open_log_file_append()` produces a blank line before the separator regardless of whether existing content ends with a newline.
