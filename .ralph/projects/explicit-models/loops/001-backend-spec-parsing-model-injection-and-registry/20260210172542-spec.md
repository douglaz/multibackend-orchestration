# Feature: Backend Spec Parsing, Model Injection, and Registry Support

## Description
Implement the core `BackendSpec` parsing system (`parse_backend_spec`), update `CliBackend` construction to support model injection via `--model` CLI args, extend `BackendRegistry` with `get_or_create_for_spec()` to dynamically create model-specific backends, update `opposite()` and `assign_*_backends()` to handle spec strings, and update config validation in `resolve_effective_config()` to parse the spec before validating the base backend name. This is the complete implementation of the explicit model selection feature — parsing, injection, registry, backend assignment propagation, state recording, and config validation — delivered as a single cohesive change since all pieces are tightly interdependent.

## Acceptance Criteria
- [ ] `BackendSpec` struct with `name: String` and `model: Option<String>` is defined in `src/backend/mod.rs`
- [ ] `parse_backend_spec(spec: &str) -> Result<BackendSpec>` correctly parses `"claude"` → name="claude"/model=None, `"claude(opus)"` → name="claude"/model=Some("opus"), and rejects empty names or empty models
- [ ] `claude::backend_from_config` and `codex::backend_from_config` accept an optional model parameter; when provided, `--model <MODEL>` is prepended to the args list
- [ ] `CliBackend::name()` returns the full spec string (e.g. `"claude(opus)"`) when a model is set
- [ ] `BackendRegistry` gains a `get_or_create_for_spec(&mut self, spec: &str) -> Result<Arc<dyn Backend>>` method that parses the spec, reuses cached backends for the same spec, and creates new model-injected backends on demand
- [ ] `BackendRegistry::opposite()` extracts the base name from a spec string (e.g. `"claude(opus)"` → opposite is `"codex"`, not `"codex(opus)"`)
- [ ] `assign_feature_backends` and `assign_completion_backends` propagate the full spec string for the starting backend side (planner/reviewer) while the opposite side uses the bare base name
- [ ] `planner_for_loop` correctly alternates using spec strings
- [ ] `resolve_effective_config()` in `src/config/mod.rs` parses the starting_backend spec and validates the base name, so `"claude(opus)"` passes validation while `"unknown(opus)"` fails
- [ ] `BackendRegistry::new()` stores the default_backend as the full spec string (from config) so model specs in `default_backend` propagate
- [ ] State JSON records the full spec string (e.g. `"claude(opus)"`) in loop backend fields — this happens naturally since `FeatureLoopBackends` fields are `String`
- [ ] Bare backend names like `"claude"` and `"codex"` continue to work unchanged (backward compatibility)
- [ ] Unit tests for `parse_backend_spec`: bare name, name with model, empty name, empty model, missing parens edge cases
- [ ] Unit test that `BackendRegistry::opposite()` works with spec strings containing models
- [ ] Unit test or integration test verifying that a model-specified backend includes `--model` in its args
- [ ] All existing tests continue to pass
