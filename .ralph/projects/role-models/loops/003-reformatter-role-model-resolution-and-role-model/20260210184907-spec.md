# Feature: Reformatter Role-Model Resolution and Role-Model Health Checks

## Description
Wire the "reformatter" role model into `execute_with_parse_retries()` and add startup pre-creation of all role-model backends so they are health-checked before execution begins. Currently, when a parse failure triggers a reformat attempt using the opposite backend, the reformatter backend is resolved with a bare name (e.g. `"codex"`) instead of applying the configured reformatter model (e.g. `"codex(o3)"`). Additionally, role-model backends (e.g. `claude(claude-sonnet-4-5-20250929)`) are never pre-created at startup, so invalid model IDs won't fail until mid-execution. This feature addresses both gaps in a single loop since pre-creating reformatter backends at startup also resolves the `&BackendRegistry` vs `&mut BackendRegistry` mutability conflict in `execute_with_parse_retries`.

## Acceptance Criteria
- [ ] Add a `preload_role_model_backends(registry: &mut BackendRegistry)` function (in `src/workflow/orchestrator.rs`, following the `preload_override_backends` pattern) that iterates all backends in the config, reads each role model from `BackendRoleModels`, constructs the model-injected spec (e.g. `claude(claude-sonnet-4-5-20250929)`), and calls `registry.get_or_create_for_spec()` for each
- [ ] `preload_role_model_backends` is called during startup (in `Orchestrator::run`) after `preload_override_backends` and before `health_check_all()`, so all role-model backends are health-checked at startup
- [ ] `preload_role_model_backends` skips entries where the role model is `None`
- [ ] `preload_role_model_backends` covers all 5 roles (planner, implementer, reviewer, completer, reformatter) for all configured backends
- [ ] In `execute_with_parse_retries()`, the reformatter backend resolution applies the "reformatter" role model: after computing the opposite backend name, call `registry.resolve_backend_for_role(opposite_name, "reformatter")` and then use `registry.get()` on the resulting spec (which was pre-created at startup)
- [ ] When no reformatter role model is configured, behavior is unchanged (falls back to bare opposite backend)
- [ ] When no opposite backend exists, behavior is unchanged (falls back to original backend)
- [ ] Per-role backend overrides (explicit model specs) still take precedence — if the reformatter was already resolved with a model, it is not overridden
- [ ] Invalid model IDs in role-model config cause startup failure (via health check), not mid-execution failure
- [ ] All existing tests pass

- [ ] Integration/unit test: reformatter backend in `execute_with_parse_retries` uses the role-model-injected spec
