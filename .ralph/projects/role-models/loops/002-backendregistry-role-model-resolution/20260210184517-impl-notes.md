# Implementation Notes

## Decisions Made
- Implemented `resolve_backend_for_role` as a `&self` method on `BackendRegistry` (no mutation needed), keeping the signature simple and compatible with all call sites.
- Role-model injection is applied at the end of `assign_feature_backends` and `assign_completion_backends`, after alternation and per-role overrides are computed. This ensures the correct precedence: alternation → per-role override → role-model injection (only when bare).
- Explicit model specs (e.g. `claude(opus)`) pass through unchanged — `parse_backend_spec` detects the model and short-circuits. This satisfies the requirement that per-role override models are not replaced.
- Bare per-role overrides (e.g. `planner_backend = "claude"`) still receive role-model injection, since they have no explicit model after parsing.
- On parse failure or unknown backend/role, `resolve_backend_for_role` returns the input unchanged, providing safe fallback behavior.
- Did not implement the reformatter role-model resolution in `execute_with_parse_retries` (spec section 3 of master prompt) as it is explicitly out of scope for this loop's acceptance criteria ("Blocks: Reformatter role-model application in parse retries").
- Did not implement startup health-check pre-creation of role-model backends as it is also listed as blocked by this feature, not required by this loop's acceptance criteria.

## Spec Deviations
- The master prompt mentions reformatter backend resolution in `execute_with_parse_retries` and startup health checks, but the loop 2 spec's acceptance criteria explicitly scope these out ("Blocks: Reformatter role-model application in parse retries; startup role-model pre-creation/health-check coverage"). These are deferred to future loops.
- Orchestrator integration test `two_loop_happy_path_with_separate_backends` backend assertions were updated to expect model-injected specs. The mock scripts continue to work because they ignore CLI arguments and only read from stdin.
