# Feature: Multi-Backend Acceptance QA Gate

## Description
Replace the single-backend acceptance QA invocation with a serial loop over both supported backend families (`claude` and `codex`). When the completer returns `Complete` and QA is enabled, the orchestrator runs acceptance QA on both families independently, aggregates results, and only marks the project complete if all pass. This includes: modifying `build_acceptance_prompt` to accept a pre-serialized state snapshot (preventing prompt contamination between QA runs), updating `latest_completion_feedback_context` to include all failing QA artifacts in planner feedback, and adding comprehensive conformance tests.

## Acceptance Criteria
- [ ] When the completer returns `Complete` and `qa_enabled` is true, the orchestrator runs acceptance QA on both backend families (`claude` and `codex`) serially, using `resolve_backend_for_role(family, "qa")` for each
- [ ] The acceptance backend list is always `["claude", "codex"]` — it does not consult `role_overrides.qa` or derive from the completer backend
- [ ] Each QA backend produces its own artifact (`AcceptancePass` or `AcceptanceFail`) stored in the completion loop directory
- [ ] Each QA result is recorded as a separate `AcceptanceQaResult` entry in `completion.artifacts.acceptance_results` with distinct `backend` values
- [ ] `build_acceptance_prompt` accepts a pre-serialized `state_json: &str` instead of `&ProjectState`, and the state JSON is snapshotted once before the QA loop to prevent prompt contamination
- [ ] Both QA backends are invoked regardless of whether the first passed or failed; the second QA's prompt does not include the first QA's verdict or acceptance result metadata
- [ ] The project is marked `Completed` only if `acceptance_all_required_passed` returns true for both families; otherwise verdict is forced to `Continue` and phase returns to `Planning`
- [ ] Log messages identify which backend is being invoked, which passed, which failed, and the aggregate outcome
- [ ] `latest_completion_feedback_context` collects all failing acceptance QA artifacts (not just the first) and formats each as a numbered section with backend identification
- [ ] On retry after forced `Continue`, the next completion attempt starts fresh with new QA runs on both backends
- [ ] Existing test `acceptance_gate_pass` updated to assert `acceptance_results.len() == 2` with both entries passed and distinct backends
- [ ] Existing test `acceptance_gate_fail_forces_continue` updated to assert 2 acceptance results per attempt
- [ ] New test `acceptance_gate_multi_backend_one_fails`: one backend passes, other fails — asserts forced `Continue`, 2 results with distinct backends, mixed pass/fail
- [ ] New test `acceptance_gate_multi_backend_independent`: mock detects and fails if prompt contains acceptance result metadata, verifying no prompt contamination
- [ ] New test `acceptance_gate_qa_backend_override_no_duplicate`: setting `workflow.qa_backend` to same-family as completer still produces 2 distinct acceptance QA results
- [ ] New test `acceptance_gate_qa_backend_override_opposite_family`: setting `workflow.qa_backend` to opposite family still produces 2 distinct acceptance QA results
- [ ] New test `acceptance_gate_all_feedback_on_failure`: both QAs fail, planner feedback includes both failure artifacts
