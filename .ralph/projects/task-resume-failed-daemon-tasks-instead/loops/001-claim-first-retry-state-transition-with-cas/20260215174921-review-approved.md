# Review: APPROVED

## Acceptance Criteria Checklist
- [x] A `retrigger_failed_task(task_id)` function exists in `src/daemon/runtime.rs` that accepts a task ID and orchestrates the claim-first retry flow.
- [x] On re-trigger, `claim_issue(owner, repo, issue_number)` is called **before** any state transition out of `Failed` — the function loads a snapshot, validates `Failed` state, then calls `claim_issue` before entering `with_exclusive_tasks`.
- [x] If `claim_issue` fails, the task state remains `Failed`, and the function returns an error indicating claim failure — early return with `RalphError::Orchestration` and structured `event=claim_failure` log.
- [x] After successful claim, a CAS transition `Failed -> Pending` is performed using `store.with_exclusive_tasks()` that re-reads the task state and only transitions if still `Failed` — the closure re-finds the task by ID and checks `task.state != TaskState::Failed` before mutating.
- [x] If CAS fails (task no longer `Failed`), the function performs best-effort claim release (remove `ralph:in-progress` label) and returns a conflict/error — `best_effort_release_claim()` calls `github::release_claim()`, returns `RalphError::GitConflict`. Also handles `Missing` case.
- [x] Structured log messages are emitted for: claim failure (`event=claim_failure`), CAS conflict (`event=cas_conflict`), and successful retrigger (`event=success`).
- [x] A CLI subcommand `ralph daemon retrigger <task_id>` is added to `src/cli/daemon.rs` — `DaemonRetriggerArgs` struct, `DaemonCommand::Retrigger` variant, `execute_retrigger` handler.
- [x] Test `runtime_retrigger_claim_failure_preserves_failed_state` passes — mock gh exits 1 on `--add-label`, asserts task stays `failed`, claim marker exists, release marker absent, structured log present.
- [x] Test `runtime_retrigger_claim_then_cas_conflict_does_not_set_pending` passes — mock gh succeeds on claim but mutates tasks.json to `aborted` via sed side-effect, asserts task is `aborted` (not `pending`), release marker exists, structured CAS conflict log present.

## Notes

The implementation is clean and well-structured:

- **Claim-first ordering** is correctly enforced: snapshot load → state validation → `claim_issue` → `with_exclusive_tasks` CAS. The two-phase read (snapshot outside lock, re-read inside lock) is the correct CAS pattern.
- **`release_claim()`** in `github.rs` correctly mirrors `claim_issue` using `--remove-label` instead of `--add-label`.
- **CAS conflict test** uses a clever technique: the mock `gh` script mutates `tasks.json` via `sed` during the claim call, simulating a concurrent state change between claim and CAS lock acquisition. This is a valid simulation of the race condition.
- **CLI integration** follows the existing `Abort` pattern exactly (`DaemonAbortArgs` → `DaemonRetriggerArgs`, `execute_abort` → `execute_retrigger`).
- The `CasOutcome` enum scoped inside the function is a clean way to communicate the lock result without exposing internal types.
- Remaining diff changes are rustfmt reformatting of existing code (line wrapping adjustments) — no behavioral changes outside the feature scope.
