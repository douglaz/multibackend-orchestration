# Feature: Claim-first retry state transition with CAS conflict safety

## Description
Implement a `retrigger_failed_task()` function in the daemon runtime that safely transitions a `Failed` task back to `Pending` for re-dispatch. The function enforces a **claim-first** protocol: it calls `claim_issue` on GitHub before any state mutation, then performs a CAS (compare-and-swap) transition `Failed -> Pending` that double-checks the task is still in `Failed` state. If claim fails, the task stays `Failed`. If CAS fails (e.g., concurrent abort changed state), the function performs best-effort claim release and returns a conflict error without setting `Pending`. This prevents tasks from being stranded in `Pending` without a valid claim and eliminates race conditions in the retry path.

## Acceptance Criteria
- [ ] A `retrigger_failed_task(task_id)` function exists in `src/daemon/runtime.rs` that accepts a task ID and orchestrates the claim-first retry flow.
- [ ] On re-trigger, `claim_issue(owner, repo, issue_number)` is called **before** any state transition out of `Failed`.
- [ ] If `claim_issue` fails, the task state remains `Failed`, and the function returns an error indicating claim failure.
- [ ] After successful claim, a CAS transition `Failed -> Pending` is performed using `store.with_exclusive_tasks()` that re-reads the task state and only transitions if still `Failed`.
- [ ] If CAS fails (task no longer `Failed`), the function performs best-effort claim release (remove `ralph:in-progress` label) and returns a conflict/error.
- [ ] Structured log messages are emitted for: claim failure, CAS conflict, and successful retrigger.
- [ ] A CLI subcommand `ralph daemon retrigger <task_id>` (or equivalent) is added to `src/cli/daemon.rs` that invokes `retrigger_failed_task`.
- [ ] Test `runtime_retrigger_claim_failure_preserves_failed_state` passes: mock claim_issue to fail, assert task stays `Failed` and never reaches `Pending`.
- [ ] Test `runtime_retrigger_claim_then_cas_conflict_does_not_set_pending` passes: mock claim_issue to succeed, but simulate concurrent state change (task moved to `Aborted` between claim and CAS), assert task is not set to `Pending` and best-effort release is attempted.
