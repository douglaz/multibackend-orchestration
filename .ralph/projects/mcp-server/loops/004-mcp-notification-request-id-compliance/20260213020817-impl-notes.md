# Implementation Notes

## Decisions Made
- Collapsed the two separate `notifications/initialized` and `notifications/*` skip blocks into a single `starts_with("notifications/")` guard that only skips (continues) when `message.id.is_none()`. When an `id` is present, execution falls through to the existing `match` block where the `_` arm already returns `-32601 Method not found`. This is the minimal change that satisfies the spec without duplicating error-response logic.
- The `notifications/initialized` case no longer has its own dedicated check; it is subsumed by the general `notifications/*` guard. Behavior is identical: no `id` means silent ignore, with `id` means `-32601`.

## Spec Deviations
- None. All seven acceptance criteria are met exactly as specified.

## Testing
- **Existing test** (`server_dispatches_initialize_tools_list_ping_and_unknown_method`): Already covers `notifications/initialized` without `id` (silently ignored) and `notifications/custom` without `id` (silently ignored). Also covers `initialize`, `tools/list`, `ping`, and unknown `bogus/method` with `id` returning `-32601`. All 4 response assertions unchanged.
- **New test** (`notification_with_id_returns_method_not_found`): Sends `notifications/custom` *with* `"id": 99` and asserts the response has `error.code == -32601` and `error.message == "Method not found"`. Also verifies `notifications/initialized` without `id` produces no response (only 2 total responses: initialize + the error).
- `cargo test` passes: 457 tests across all crates, 0 failures.
