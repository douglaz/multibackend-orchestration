Now I have a thorough understanding of the current codebase. This is the first planning loop (loop 4, phase 1, no previous specs/loops completed). The project requires a comprehensive refactoring of the daemon runtime loop for concurrency. Given the scale, I need to decompose this into logical features and pick the right first one.

The requirements break down into these major features:
1. **Git lock safety semaphore** - Foundation: `Arc<tokio::sync::Semaphore>` with 1 permit for repo-root git ops
2. **PRD execution model** - Decouple PRD from loop (background task in continuous mode, inline in single-iteration)
3. **`kill_aborted_children` concurrency** - Concurrent label fetches via JoinSet
4. **`collect_children` concurrency** - Concurrent `complete_task` via JoinSet
5. **`dispatch_task` refactor** - Return `Result<ChildHandle>` instead of mutating `children`
6. **`poll_and_claim` concurrency** - Concurrent dispatch after sequential claim
7. **`auto_rebase_phase` concurrency** - Concurrent rebase operations via JoinSet
8. **Tests** - Integration/validate tests for all new concurrent behavior

The git lock semaphore is the foundational piece that other concurrent features depend on (dispatch and rebase both need it). The `dispatch_task` refactor (returning `Result<ChildHandle>`) is a prerequisite for concurrent dispatch in `poll_and_claim`. The PRD decoupling is independent.

The best first feature is the **git lock safety semaphore + `dispatch_task` refactor** since these are prerequisites for the concurrent dispatch/rebase work, and together they form a coherent unit.

# Feature: Git Semaphore and dispatch_task Decoupling

## Description
Introduce a shared `Arc<tokio::sync::Semaphore>` with 1 permit in the `run()` function to serialize repo-root git operations, and refactor `dispatch_task` to return `Result<ChildHandle>` instead of mutating `children` directly. This creates the foundation for all subsequent concurrency work by (a) providing a coordination primitive that prevents git index lock contention when dispatch and rebase operations run concurrently, and (b) making `dispatch_task` pure with respect to the children map so the caller can run multiple dispatches concurrently and insert results sequentially.

## Acceptance Criteria
- [ ] A new `prd_shutdown_timeout_secs: u64` field is added to `DaemonRuntimeConfig` with default 60 and minimum 1, wired through from CLI/config construction sites.
- [ ] An `Arc<tokio::sync::Semaphore>` with 1 permit is created in `run()` before the main loop.
- [ ] The semaphore is passed (as `Arc<tokio::sync::Semaphore>`) into `dispatch_task` and `auto_rebase_phase` (and any helper they call that performs repo-root git operations).
- [ ] `dispatch_task` signature changes: it no longer takes `children: &mut HashMap<u32, ChildHandle>` and instead returns `Result<ChildHandle>`.
- [ ] `dispatch_task` acquires the semaphore permit before repo-root git operations (`ensure_repo_ready`, `create_worktree`, `sync_project_branch`) and releases it before long worktree-local work (refinement, spawn, watcher setup).
- [ ] The caller in `poll_and_claim` inserts the returned `ChildHandle` into `children` on success, and performs the `ralph:in-progress` → `ralph:failed` rollback on failure (preserving existing behavior exactly).
- [ ] `auto_rebase_phase` acquires the semaphore for `git fetch` in the repo root but does NOT hold it across `git rebase` or `git push` inside worktrees.
- [ ] `ensure_repo_ready` (in `bootstrap`) acquires the semaphore when called from dispatch context.
- [ ] Worktree add/remove/prune operations acquire the semaphore since they modify repo-root state.
- [ ] Existing sequential behavior is fully preserved — all tests continue to pass with no observable behavior change.
- [ ] All existing unit and integration tests pass (`nix develop -c cargo test`).
- [ ] The project builds cleanly (`nix build -L`).

## Files to Modify/Create
- `src/daemon/runtime.rs` — Create semaphore in `run()`, thread it through to `dispatch_task`, `auto_rebase_phase`, `poll_and_claim`, `collect_children` (for worktree cleanup). Change `dispatch_task` signature to return `Result<ChildHandle>`. Update `poll_and_claim` to insert ChildHandle and handle rollback. Add `prd_shutdown_timeout_secs` to config struct.
- `src/daemon/mod.rs` — No structural changes needed but may need re-exports if semaphore type appears in public API.
- `src/daemon/bootstrap.rs` — Update `ensure_repo_ready` to accept an optional semaphore parameter for guarding its repo-root git operations.
- `src/daemon/worktree.rs` — Update `create_worktree`, `remove_worktree` to accept semaphore for guarding worktree add/remove/prune (repo-root git state).
- `src/daemon/cli.rs` (or equivalent config construction) — Wire `prd_shutdown_timeout_secs` from CLI flags/config to `DaemonRuntimeConfig`, defaulting to 60.
- `tests/` or `src/daemon/runtime.rs` (test modules) — Update any tests that construct `DaemonRuntimeConfig` to include the new field. Verify dispatch_task return-value contract.

## Dependencies
- Requires: none (first feature in the refactoring sequence)
- Blocks: concurrent `poll_and_claim` dispatch (needs semaphore + dispatch returning ChildHandle), concurrent `auto_rebase_phase` (needs semaphore threading), PRD background task decoupling (needs `prd_shutdown_timeout_secs` config), concurrent `kill_aborted_children` (independent but benefits from established patterns), concurrent `collect_children` (independent but cleanup needs semaphore)
