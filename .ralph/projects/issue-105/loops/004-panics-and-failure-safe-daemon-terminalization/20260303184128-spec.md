# Feature: Panics-and-failure-safe daemon terminalization recovery

## Description
Implement deterministic rollback/terminalization for `poll_and_claim` dispatch workers and `collect_children` completion workers when failures occur as panics, so no issue can remain `ralph:in-progress` due to worker panics. This hardens the concurrency refactor by making every asynchronous worker outcome carry issue identity and explicit success/failure meaning, then applying the same per-issue rollback semantics used for normal errors. It also strengthens conformance tests with deterministic fault injection so concurrency and failure-path behavior are proven, not inferred.

## Acceptance Criteria
- [ ] `dispatch_task` worker execution in `poll_and_claim` must return a per-issue outcome struct containing `issue_number` and either `child_handle` or failure detail (including a distinct panic path).
- [ ] If a dispatch worker returns `Err`, current rollback semantics must remain unchanged (`ralph:in-progress -> ralph:failed`) and be applied on a per-issue basis.
- [ ] If a dispatch worker panics, the panic must be captured and converted into a failure outcome that includes `issue_number`, then handled with the same rollback path as an `Err`.
- [ ] If rollback for one issue fails, that failure must be logged, that issue must remain recoverable by state (not silently dropped), and processing of other issues must continue.
- [ ] `collect_children` must continue to preserve ordered teardown side effects per child (`watcher_cancel -> watcher_join -> draft_pr_cancel -> draft_pr_join`) while making terminalization (`complete_task`) concurrent via `JoinSet` outcomes.
- [ ] If a completion worker panics or errors, the issue must be explicitly transitioned to a terminal failure state (at minimum `ralph:failed`) using captured `issue_number`, with no child left unprocessed in the same cycle.
- [ ] A panic inside one completion worker must not prevent terminalization/rollback processing for remaining finished children discovered in that iteration.
- [ ] `poll_and_claim` continues sequential claim/label-swap and issue extraction, with concurrent dispatch launch still capped by slots.
- [ ] Validate conformance tests must deterministically inject dispatch-failure before child spawn and assert explicit dispatch-failure markers plus per-issue label rollback.
- [ ] Validate conformance tests must include concurrency evidence (e.g., overlapping execution markers/timing) to distinguish concurrent dispatch from purely sequential behavior.
- [ ] Validate conformance tests must include a completion panic/error scenario proving issue terminalization happens and state does not remain stuck in `ralph:in-progress`.
