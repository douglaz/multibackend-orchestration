# Implementation Notes

## Decisions Made

1. **SessionRecord/SessionStore placement**: Added to `src/project/state.rs` co-located with other state types. `SessionStore` uses a flat `Vec<SessionRecord>` for simplicity and serde compatibility. Lookup is by `(loop_number, role, backend_spec)` triple via `.iter().find()` which is O(n) but adequate for the expected small record counts per project.

2. **Config 4-layer resolution**: Followed the existing precedence pattern (CLI override > project > global > default) identically for all 4 new fields: `session_reuse_enabled`, `session_reuse_roles`, `session_reuse_reset_on_prompt_change`, `session_reuse_reset_on_rollback`. Defaults: enabled=false, roles=["implementer","reviewer","qa"], both reset flags=true.

3. **Role validation**: `KNOWN_ROLES` constant (`planner|implementer|reviewer|qa|completer`) with validation in `parse_session_reuse_roles`. Invalid roles return `RalphError::Validation`.

4. **Arg rewriting architecture**: `BackendInvocationContext` struct carries `session_id`, `loop_dir`, `role`, `json_output_required`. `CliBackend::effective_args()` dispatches to `effective_args_claude()` or `effective_args_codex()` based on backend name. No-session invocations return unchanged args.

5. **Claude rewrite rules**: Remove `-p` (require its presence), strip existing `--resume`/`--output-format` args, append fresh `--resume <id>` and `--output-format json`. Handles both `--flag value` and `--flag=value` forms.

6. **Codex rewrite rules**: Require trailing `-` (stdin marker), rewrite to `exec resume <id> ... --json -`, strip existing `--json` and `exec` subcommand args, ensure `-` is last token.

7. **Output normalization**: New `src/backend/output_normalizer.rs` module. Detects Claude JSON (single object with `content` array), Codex JSONL (newline-delimited objects with `type` fields), and raw text. Extracts `session_id`/`thread_id`, usage tokens, and assistant message text. Malformed input falls back to raw text without panic.

8. **Normalization integration**: Applied inside `execute_with_parse_retries()` — every backend execution attempt is normalized before the parse function consumes it. On normalization error, falls back to raw stdout.

9. **Tmux backend session-aware args**: Extended `TmuxExecutionContext` with `session_id` field. `build_shell_command` delegates to `effective_args()` when session_id is present; on rewrite failure, falls back to default args.

10. **Rollback session invalidation**: Loops > target have sessions removed unconditionally. Target loop sessions cleared only when `session_reuse_reset_on_rollback=true`. Effective config is loaded in rollback to check the flag.

11. **Prompt-change session invalidation**: `handle_prompt_change()` received new `session_reuse_reset_on_prompt_change` parameter. On `RestartLoop` action, current-loop sessions are cleared when the flag is true.

12. **Bootstrap hash**: `compute_bootstrap_hash()` uses `sha256_hex("{role}|{backend_spec}|{prompt_hash_at_loop_start}|{spec_hash}|{template_hash}|sessions-v1")`. The function is implemented and ready for wiring into the session lookup path.

13. **cwd debug_assert**: Added in `execute_with_parse_retries()` under `#[cfg(debug_assertions)]` to verify working directory stability before backend invocation.

## Spec Deviations

1. **Session lookup/store at call sites not yet wired**: The `session_reused_this_call` parameter at each call site still defaults to `false`. The infrastructure is in place (bootstrap hash computation, session store lookup/upsert, normalization extracting session_id), but the per-call-site wiring to do actual session lookup → arg rewrite → result store is deferred to the next iteration. This is because the orchestrator has 9 separate backend invocation sites with varying context, and wiring each correctly requires careful testing of the interaction between session state and parse retries.

2. **`is_session_reuse_enabled_for_role` not yet called**: The helper function exists but the orchestrator doesn't yet gate session lookups on it. Marked `#[allow(dead_code)]` for now.

3. **Conformance tests are config/integration-level**: The 6 conformance tests validate config get/set/show, state.json structure, rollback behavior, and cwd stability. The session lifecycle store-and-resume test validates the data model but doesn't exercise actual backend session resumption (which requires the call-site wiring from deviation #1).
