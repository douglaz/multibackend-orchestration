# Feature: Session-Aware Parse Retries & Token Metrics (E + F)

## Description
Upgrade the parse-retry pipeline from 3 attempts to a session-aware 4-attempt sequence and add per-attempt token metrics logging. When a session ID is available after attempt 1, insert a new attempt 2 that resumes the same backend session with a short correction prompt before falling back to the opposite-backend reformatter. After every normalization call on every attempt, emit a structured `tracing::info!` event carrying role, phase, loop number, 1-based attempt index, backend name, session-reused flag, and the three token counters (tokens_in, tokens_out, cached_in) extracted by the existing normalizer.

## Acceptance Criteria
- [ ] Parse-retry pipeline executes 4 attempts when a session ID is active after attempt 1 normalization: (1) initial execution → normalize → parse, (2) session follow-up via resume with short correction prompt on same backend → normalize → parse, (3) opposite-backend reformatter → normalize → parse, (4) reminded full prompt on original backend as a fresh call (session_id=None) → normalize → parse.
- [ ] Without a session ID, the pipeline executes attempts 1, 3, and 4 only (skipping the session follow-up), for a total of 3 attempts.
- [ ] If attempt 1 parse fails but normalization yields a new session ID, attempt 2 uses that new session ID immediately for the resume call.
- [ ] Attempt 4 always uses `session_id=None` (fresh call) to avoid compounding bad session state.
- [ ] `ParseRetriesExhausted.attempts` equals the actual number of attempts executed (3 without session, 4 with session).
- [ ] After every `normalize_output` / `normalize_backend_output` call on every attempt (including reformatter attempts), a `tracing::info!` event is emitted with fields: `role`, `phase`, `loop_number`, `attempt` (1-based within parse-retry sequence), `backend`, `session_reused` (true only when resume args were actually used for that attempt), `tokens_in`, `tokens_out`, `cached_in`.
- [ ] When token fields are unavailable (e.g. non-JSON fallback), they are omitted via `tracing::field::Empty` rather than logged as zero.
- [ ] The short correction prompt for attempt 2 is a concise message instructing the backend to reformat its previous response in the expected structure, not a full re-prompt.
- [ ] Existing empty-output guard (retry on <20 chars) still fires before entering the retry sequence.
- [ ] All existing conformance and unit tests continue to pass.
- [ ] New unit tests cover: attempt-count semantics (`attempts=3` without session, `attempts=4` with session), token logging includes correct `attempt` number and `session_reused` flag for each attempt, session follow-up attempt uses the session ID from attempt 1 normalization.

## Files to Modify/Create
- `src/workflow/orchestrator.rs` — Restructure `execute_with_parse_retries` to support the 4-attempt session-aware pipeline; insert session follow-up attempt 2 between current attempt 1 and reformatter; add `tracing::info!` calls after every normalization with all required fields; pass role/phase/loop_number/backend metadata into the retry function or capture from surrounding context; ensure attempt 4 forces `session_id=None`.
- `src/workflow/prompts.rs` (or wherever correction prompt text lives) — Add a short correction/reformat prompt template for the session follow-up attempt 2 (e.g. "Your previous response could not be parsed. Please reformat it as …").
- `src/backend/mod.rs` — Potentially adjust `BackendInvocationContext` or `effective_args` to support the fresh-call override for attempt 4 (forcing no resume even when a session record exists).

## Dependencies
- Requires: Loop 4 (Session Reuse v1 Core — provides `NormalizedOutput` with token fields, `BackendInvocationContext`, `effective_args`, session store, and the 3-attempt baseline pipeline)
- Blocks: none (final feature set)
