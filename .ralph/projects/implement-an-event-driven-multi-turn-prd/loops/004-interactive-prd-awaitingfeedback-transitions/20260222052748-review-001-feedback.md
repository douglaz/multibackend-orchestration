# Review: SUGGESTIONS

## Required Changes
1. **AwaitingFeedback approval trigger semantics**
   - Current: `src/daemon/interactive_prd.rs:679` to `src/daemon/interactive_prd.rs:684` transitions to `Done` only when `has_approval && !has_non_approval`. If one new comment is approval and another is regular feedback, it goes down the revision path.
   - Expected: Transition to `Done` when any new unprocessed non-bot comment passes `detect_approval()`. Revision path should run only when there are new comments and none are approvals.
   - Reference: Feature spec acceptance criteria "Approval by comment is supported … evaluated with `detect_approval()`" and "When new feedback exists without approval … revision prompt"; master prompt transition rules 3 and 4.

2. **Approval-path error handling bypasses retry/failure accounting**
   - Current: `src/daemon/interactive_prd.rs:758`, `src/daemon/interactive_prd.rs:762`, and `src/daemon/interactive_prd.rs:763` intentionally ignore GitHub errors during status-approved comment posting and label updates, then still persist terminal `Done`.
   - Expected: Propagate these failures so `finish_transition()` can increment `error_count`, persist `last_error`, and trigger `Failed` on threshold as specified for AwaitingFeedback stage errors.
   - Reference: Feature spec acceptance criterion "Errors in AwaitingFeedback follow existing retry accounting … on threshold (`>=3`) issue transitions to `Failed` …".

## Recommended Improvements
1. Add one integration/conformance case with mixed new comments (`"LGTM"` + separate non-approval feedback) to lock in the approval-vs-revision rule.
2. Add a test that forces approval-path GitHub mutation failure and verifies `error_count` increments (instead of terminal `Done`).
