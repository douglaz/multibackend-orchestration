# Implementation Notes

## Decisions Made
- The `AwaitingFeedback` transition handler was added as a new `transition_awaiting_feedback` / `do_awaiting_feedback` function pair, mirroring the pattern used by `Pending` and `AwaitingAnswers` transitions. This keeps the code consistent and maintainable.
- Approval detection logic: when new comments contain a mix of approval and non-approval comments, the code treats this as a revision scenario rather than approval. This follows the spec requirement that mixed positive+negative signals are treated as non-approval.
- Label-based approval (`ralph:prd-approved`) is checked first, before comment scanning. This ensures that even without new comments, a label added by a user triggers the Done transition.
- The `FEEDBACK_REVISION_PROMPT` is a separate template from `REVISION_PROMPT` (used for internal writer/reviewer loop). The feedback prompt takes `{{spec}}` + `{{feedback}}` while the internal revision prompt takes `{{idea}}` + `{{spec}}` + `{{issues}}`. This separation keeps the user-facing feedback revision distinct from the internal quality loop.
- The `do_approval_transition` helper is shared between comment-based and label-based approval paths, avoiding duplication.
- The `find_new_feedback_comments` function returns all non-bot comments after `last_processed_comment_id` (chronological order maintained by the upstream fetch), enabling aggregation of multiple feedback comments in a single revision.
- The revision generation reuses `run_draft_with_section_retry_sync` and the reviewer/section-validation loop from the existing draft generation flow, honoring `max_revisions` and `backend_timeout_secs`.
- Added public `prd_status_approved_marker()` helper for use in conformance tests.
