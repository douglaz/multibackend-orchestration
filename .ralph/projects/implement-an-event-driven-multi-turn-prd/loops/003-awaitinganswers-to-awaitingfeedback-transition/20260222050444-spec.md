# Feature: AwaitingAnswers to AwaitingFeedback Transition

## Description
Implement the `AwaitingAnswers → AwaitingFeedback` state transition in the interactive PRD workflow. When the daemon detects a new non-bot user comment posted after the questions comment (`questions_posted_at`), it extracts the user's answers and generates a draft engineering specification using the existing quick-prd writer/reviewer pipeline. The draft is posted as an idempotent comment with a versioned marker, and the persisted state is updated to `AwaitingFeedback`.

This transition requires:
1. Fetching issue comments and filtering out bot comments to find user answers.
2. Determining the daemon's own GitHub login to identify bot comments.
3. Generating a draft spec by calling the writer backend with the issue context + user answers, then validating via the reviewer backend and `check_spec_sections()`.
4. Respecting `daemon_prd_max_revisions` for internal writer/reviewer retries.
5. Posting the draft comment with an idempotent marker `<!-- ralph:prd:{issue_number}:draft-v{n} -->`.
6. Persisting `draft_revision`, `latest_draft_comment_id`, `latest_draft_body`, `user_answers`, and `last_processed_comment_id`.

## Acceptance Criteria
- [ ] `advance_issue()` dispatches to a new `transition_awaiting_answers_to_awaiting_feedback()` function when state is `AwaitingAnswers`.
- [ ] Bot comments are identified by comparing `author_login` against the daemon's GitHub login (obtained via `gh api user -q .login` or equivalent, cached per poll cycle).
- [ ] The first non-bot comment with `created_at` after `questions_posted_at` is detected as the user's answer.
- [ ] If no qualifying user comment exists, the transition is a no-op (remains `AwaitingAnswers`).
- [ ] User answer text is extracted from the qualifying comment body.
- [ ] A draft spec is generated using the configured `writer_backend` with a prompt containing: original issue text, questions asked, and user answers.
- [ ] The draft is validated using `check_spec_sections()` with retry (up to 2 retries for missing sections, matching existing `run_draft_with_section_retry` pattern).
- [ ] The draft is then reviewed using the configured `reviewer_backend` via `run_review_with_retry()` pattern, and revised if rejected, up to `max_revisions` internal iterations.
- [ ] The final draft is posted as a comment with marker `<!-- ralph:prd:{issue_number}:draft-v1 -->` (idempotent via `post_comment_with_marker()`).
- [ ] State is updated: `state = AwaitingFeedback`, `draft_revision = 1`, `latest_draft_comment_id`, `latest_draft_body`, `user_answers`, `last_processed_comment_id` (set to the answer comment's ID), `last_advanced_at`.
- [ ] Error handling follows the same pattern as `transition_pending_to_awaiting_answers`: recoverable errors increment `error_count`, 3 consecutive errors trigger `transition_to_failed()`.
- [ ] All backend calls respect the `backend_timeout_secs` deadline.
- [ ] Unit tests cover: answer comment detection (with bot filtering), draft generation prompt construction, no-op when no user comment exists, error accumulation and failure transition.
- [ ] Integration test added: simulated flow from `AwaitingAnswers` state with mock comments producing a draft.
- [ ] Conformance test added: `answer_to_draft` covering the full AwaitingAnswers → AwaitingFeedback path.
