# Implementation Notes

## Decisions Made
- **Backend execution in PRD transitions**: Used the same `CliBackend` pattern as `daemon/refine.rs` — create backends via `claude::backend_from_config()` / `codex::backend_from_config()` from the global config. This avoids requiring the full `BackendRegistry` infrastructure which is designed for orchestrator-level session management.
- **Blocking execution model**: Since the daemon wraps PRD poll/advance in `spawn_blocking_op()`, and backend calls are inherently async, we create a lightweight `tokio::runtime::Builder::new_current_thread()` inside the blocking context to drive `backend.execute()` with timeout. This preserves the existing daemon architecture where each phase runs as a blocking task.
- **Question synthesis backend**: Uses the first configured question backend (Backend A) for the synthesis pass, since both backends are validated at startup and the spec doesn't specify which to use for synthesis.
- **PRD label conflict prevention**: Added `interactive_prd::has_prd_label()` check in `poll_and_claim()` to explicitly skip issues carrying any PRD label from the normal `ralph:ready` claim flow, even though the existing `filter_claimable` logic would catch most cases. This provides defense-in-depth against edge cases where `ralph:ready` and `ralph:prd` coexist.
- **Error recovery strategy**: Recoverable errors increment `error_count` and persist state for retry next tick. On 3 consecutive failures for the same stage, the issue transitions to `Failed` with an error comment marker and `ralph:prd-failed` label.
- **Active issue polling**: The PRD phase polls both `ralph:prd` (for new pickups) and `ralph:prd-active` (for in-progress issues) to support future transitions (AwaitingAnswers -> AwaitingFeedback, etc.) in subsequent loops.

## Spec Deviations
- **AwaitingAnswers and AwaitingFeedback transitions**: Only the `Pending -> AwaitingAnswers` transition is fully implemented as specified for this loop. The `AwaitingAnswers -> AwaitingFeedback` and feedback revision transitions are stubbed as no-ops in `advance_issue()` since they are explicitly listed as blocked by this feature ("Blocks: Answer-to-draft generation"). The state machine and persistence infrastructure supports them.
- **Comment ID from `post_comment_with_marker`**: The spec says to persist `questions_comment_id`. Since `gh issue comment` doesn't directly return the comment ID, we post the comment and then fetch it back by searching for the marker. This adds one extra API call but ensures we always have the correct ID.
- **Structured comment `id` field**: GitHub's `gh` CLI returns comment IDs as integers in JSON. We deserialize these and use them in `IssueComment.id`. The `RawComment` struct handles optional fields gracefully since different GitHub API versions may vary slightly in response format.
