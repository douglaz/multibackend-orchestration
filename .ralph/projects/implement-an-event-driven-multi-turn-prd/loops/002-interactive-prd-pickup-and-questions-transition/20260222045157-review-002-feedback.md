# Review: SUGGESTIONS

## Required Changes

1. **Pending retry semantics can orphan PRD issues after partial label failure**
   - Current: `do_pending_to_awaiting` removes `ralph:prd` best-effort, then tries to add `ralph:prd-active` (`src/daemon/interactive_prd.rs:430`, `src/daemon/interactive_prd.rs:434`). If add fails after remove succeeds, state is persisted as recoverable error, but future polls only query `ralph:prd`/`ralph:prd-active` (`src/daemon/interactive_prd.rs:301`, `src/daemon/interactive_prd.rs:317`), so the issue may never be retried and can't reach the `error_count >= 3` failure path.
   - Expected: preserve retry visibility on errors (for example: add active before removing prd, or rollback/re-add `ralph:prd` when add-active fails) so recoverable failures are retried next tick and can escalate to `Failed`.
   - Reference: Feature spec acceptance criterion "recoverable errors retry next tick; on 3 consecutive stage failures transition to Failed".

2. **New conformance test currently fails due substring matching bug**
   - Current: `startup_prd_label_ensure` counts matches with `line.contains("create ralph:prd")`, which also matches `ralph:prd-active`, `ralph:prd-approved`, etc. (`src/validate/tests_interactive_prd.rs:393`). This makes `interactive_prd::startup_prd_label_ensure` fail.
   - Expected: use exact token matching/parsing for the label argument so each label is counted once.
   - Reference: Acceptance criterion "Existing tests pass". Verified failure with `nix develop -c cargo run -- validate --bin ./target/debug/ralph --filter interactive_prd::`.

3. **Missing required conformance coverage for first pickup/question posting**
   - Current: registered tests in `src/validate/tests_interactive_prd.rs:14` cover startup labels, conflict handling, and state reprocessing, but there is no daemon conformance case that exercises `Pending -> AwaitingAnswers` and asserts one `questions-v{n}` marker post plus transition effects.
   - Expected: add a conformance test that mocks a `ralph:prd` issue, runs one/two daemon ticks, and verifies idempotent questions posting + active label/state progression.
   - Reference: Loop feature spec acceptance criterion requiring conformance coverage for "first pickup/question posting" and idempotent reprocessing.
