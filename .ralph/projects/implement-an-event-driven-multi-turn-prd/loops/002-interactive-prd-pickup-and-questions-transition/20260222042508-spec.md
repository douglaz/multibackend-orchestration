# Feature: Interactive PRD Pickup and Questions Transition

## Description
Loop 1 already delivered the interactive PRD foundation (`InteractivePrdState`, persistence, config, approval helper, and module wiring).  
The next logical feature is the first runtime slice: detect `ralph:prd` issues, transition `Pending -> AwaitingAnswers`, generate/post idempotent clarifying questions, and persist restart-safe state without regressing the existing `ralph:ready` workflow.

## Acceptance Criteria
- [ ] Daemon startup ensures PRD lifecycle labels exist idempotently: `ralph:prd`, `ralph:prd-active`, `ralph:prd-approved`, `ralph:prd-done`, `ralph:prd-failed`.
- [ ] Runtime adds an interactive-PRD poll phase gated by `daemon_prd_enabled`; when disabled, behavior is unchanged.
- [ ] PRD phase polls open issues with `ralph:prd`, loads existing per-issue state (or initializes `Pending`), and performs at most one state transition per issue per tick.
- [ ] `Pending -> AwaitingAnswers` transition swaps labels (`ralph:prd` removed, `ralph:prd-active` added) and removes `ralph:ready` if present.
- [ ] Clarifying questions are generated via two configured question backends plus a synthesis pass (dedupe + prioritize into one numbered list).
- [ ] All backend work inside one transition is bounded by `daemon_prd_backend_timeout_secs` as a total wall-clock budget.
- [ ] Questions comment is posted with marker `<!-- ralph:prd:{issue_number}:questions-v{n} -->`; if marker already exists, no duplicate comment is created.
- [ ] Transition persists `questions_comment_id`, `questions_posted_at`, `question_revision`, `last_advanced_at`, and `state=AwaitingAnswers` atomically.
- [ ] Recoverable transition errors persist `error_count`/`last_error`; on 3 consecutive stage failures, issue transitions to `Failed`, posts `<!-- ralph:prd:{issue_number}:status-failed -->`, and applies `ralph:prd-failed`.
- [ ] Existing `ralph:ready` workflow does not claim issues carrying PRD labels (prevents dual workflow ownership).
- [ ] Conformance coverage is added for startup label creation, first pickup/question posting, idempotent reprocessing, and `ralph:prd` + `ralph:ready` conflict handling.

## Files to Modify/Create
- `src/daemon/interactive_prd.rs` - Add runtime transition logic for `Pending -> AwaitingAnswers`, question-generation prompts/helpers, timeout-bounded backend orchestration, idempotent marker handling, and stage error/failure handling.
- `src/daemon/runtime.rs` - Invoke interactive-PRD phase in each poll cycle (before normal claim/dispatch), enforce one-transition-per-issue-per-tick behavior, and preserve existing daemon flow.
- `src/daemon/github.rs` - Add structured issue-comment fetch helpers (`id`, `author_login`, `body`, `created_at`), marker lookup helpers, and startup label ensure integration for PRD labels.
- `src/cli/daemon.rs` - Ensure startup label preflight includes PRD labels and plumb effective PRD daemon settings into runtime.
- `tests/daemon_interactive_prd.rs` - Add integration tests for pickup flow, idempotent restart behavior, and label conflict behavior.
- `src/validate/tests_interactive_prd.rs` - Create validate conformance tests for pickup/question posting and idempotency scenarios.
- `src/validate/mod.rs` - Register `tests_interactive_prd::tests()`.

## Dependencies
- Requires: Interactive PRD State Machine Foundation
- Blocks: Answer-to-draft generation (`AwaitingAnswers -> AwaitingFeedback`), feedback revision loop, approval completion path (`AwaitingFeedback -> Done`)
