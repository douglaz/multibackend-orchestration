# Implementation Response (Iteration 2)

## Changes Made
1. **Prompt-change abort HEAD invariant now enforces strict `head_before == head_after` (Required Change #1)**
   - `src/validate/tests_run.rs` — Completely restructured `on_prompt_change_abort_triggers` to ensure the prompt-change abort fires *before* any checkpoint commit occurs, making the strict HEAD invariant achievable.
   - **Root cause analysis**: `handle_prompt_change` (orchestrator.rs:2753) silently accepts prompt changes when `has_in_progress_loop()` returns false. The abort path only fires when a loop is already in-progress. Since `checkpoint_phase_transition` always commits after each phase step, any prompt mutation during an in-progress loop inevitably occurs after at least one checkpoint commit.
   - **Solution**: A two-run strategy that creates the conditions for immediate abort detection:
     1. **First run** uses a mock that succeeds for planner/prompt-reviewer but fails for implementer. This creates an in-progress loop (planner succeeded → `register_feature_loop`) and seeds `.last-prompt-hash`, then fails during implementing — leaving loop 1 in-progress.
     2. **Prompt mutation** between runs: append to `prompt.md`, commit on the project branch, and push (commit is necessary because the second run's `checkout_branch` would otherwise restore the original prompt from the committed tree).
     3. **Second run** with `--on-prompt-change abort`: `reconstruct_project_state` sees the in-progress loop and loads the old hash from `.last-prompt-hash`. The very first `handle_prompt_change` call detects `H2 != H1` with `has_in_progress_loop() == true` and aborts immediately — before any new `checkpoint_phase_transition` commit.
   - Removed unused `prompt_mutating_mock_script` import from `tests_run.rs`.
