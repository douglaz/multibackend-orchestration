# Feature: QA Acceptance Gate for Completion Phase

## Description
Loops 1–2 delivered QA schema/config plumbing (Phase 1), the runtime QA gate with feedback loop (Phase 2), and UX/reporting updates (Phase 4). The one remaining piece is Phase 3: the acceptance gate that runs QA when the completer signals `COMPLETE`. This feature adds acceptance-time QA execution inside `Phase::Completing`, writes `AcceptancePass`/`AcceptanceFail` artifacts, forces `Continue` on acceptance failure with a route back to planning, and injects acceptance-failure context into the planner prompt so failure details are not lost across the completion-to-planning boundary.

## Acceptance Criteria
- [ ] When completer returns `Complete` and `qa_enabled` is true, the orchestrator invokes the QA backend with an acceptance-oriented prompt before finalizing project completion
- [ ] Acceptance QA prompt includes: master prompt, a summary of all completed feature loops, the full current git diff against the base, and an instruction to verify overall project acceptance (not just a single feature)
- [ ] On QA PASS: writes `ArtifactKind::AcceptancePass` artifact, stores path in `CompletionLoopArtifacts.acceptance_result`, sets `acceptance_passed = Some(true)`, and keeps `ProjectStatus::Completed`
- [ ] On QA FAIL: writes `ArtifactKind::AcceptanceFail` artifact, stores path in `CompletionLoopArtifacts.acceptance_result`, sets `acceptance_passed = Some(false)`, forces `CompletionVerdict::Continue`, sets `ProjectStatus::InProgress`, and routes to `Phase::Planning`
- [ ] When completer returns `Complete` and `qa_enabled` is false, behavior is unchanged (no acceptance gate, project completes immediately)
- [ ] Acceptance QA uses the same `execute_with_parse_retries()` path and `QaDecision` parser as the feature-loop QA phase
- [ ] `build_planner_prompt()` includes a "Completion Feedback" context section when the most recent completion loop has an acceptance-fail artifact, containing both the completer verdict artifact content and the acceptance-fail artifact content
- [ ] Acceptance QA backend resolution follows the same precedence as feature-loop QA (override > planner-aligned default)
- [ ] `tests/orchestrator.rs` includes `acceptance_gate_pass_keeps_completed` test: completer says COMPLETE, QA passes, project status remains Completed
- [ ] `tests/orchestrator.rs` includes `acceptance_gate_fail_overrides_complete_to_continue` test: completer says COMPLETE, QA fails, verdict forced to Continue, project goes back to Planning
- [ ] `tests/orchestrator.rs` includes `planner_receives_acceptance_failure_context` test: after acceptance failure routes back to planning, the planner prompt includes the acceptance-fail content

## Files to Modify/Create

- `tests/orchestrator.rs` — Add `acceptance_gate_pass_keeps_completed`, `acceptance_gate_fail_overrides_complete_to_continue`, and `planner_receives_acceptance_failure_context` tests with appropriate mock backend scripts
