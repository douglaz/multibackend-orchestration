# Feature: QA Runtime Gate and Feedback Loop

## Description
Loop 1 completed the QA schema/config/backend plumbing, but runtime QA behavior is still missing (`Phase::QA` is not implemented and parser/template/init wiring is absent). Implement the Phase 2 feature that makes QA an executable gate between implementation and review, including structured QA pass/fail parsing, implementer response handling for QA failures, and iteration-limit enforcement.

## Acceptance Criteria
- [ ] `src/workflow/parser.rs` defines `QaDecision` (`Pass { body }` / `Fail { body }`) and `parse_qa_output(raw: &str)` with strict contract validation:
- [ ] PASS requires H1 `# QA: PASS` plus `## Tests Run` and `## Verification Summary`.
- [ ] FAIL requires H1 `# QA: FAIL` plus `## Failures` and `## Suggested Fixes`.
- [ ] QA parser has unit tests for pass, fail, and malformed output (parse error path).
- [ ] `src/prompts/templates.rs` adds `default_qa_template()` with guardrails: run available checks, report concrete commands/results, do not edit source files.
- [ ] `src/cli/init.rs` writes `templates/qa.md` during init, and init tests verify it exists.
- [ ] `src/workflow/orchestrator.rs` changes initial Implementing exit so `qa_enabled=true` transitions to `Phase::QA` (after staging), while `qa_enabled=false` preserves current Implementing -> Reviewing flow.
- [ ] Implementing phase handles `pending_qa_feedback` by generating an implementer response to QA fail feedback, writing `ArtifactKind::ImplQaResponse`, attaching it to latest `QaExchange.implementer_response`, clearing `pending_qa_feedback`, and returning to `Phase::QA` with incremented iteration.
- [ ] New `Phase::QA` arm executes QA backend with prompt context including master prompt, spec, impl notes, current git diff, and prior QA history.
- [ ] QA PASS writes `ArtifactKind::QaPass`, appends `QaExchange { passed: true, ... }`, transitions to Reviewing, and resets `phase_iteration=1`.
- [ ] QA FAIL writes `ArtifactKind::QaFail`, appends `QaExchange { passed: false, ... }`, sets `pending_qa_feedback` to the fail artifact path, and transitions to Implementing for response.
- [ ] QA iteration limit enforces `max_qa_iterations`; on overflow rollback current loop and return `QaIterationLimitExceeded` (or continue when `--until-complete`, matching review-limit behavior).
- [ ] `expected_format_template_for("qa", None)` returns QA pass/fail format guidance for parse-retry flow.
- [ ] `dry_run_summary()` includes QA backend when QA is enabled.
- [ ] QA executions set tmux context role label to `qa`.
- [ ] `tests/orchestrator.rs` covers: `qa_disabled_skips_phase`, `qa_pass_proceeds_to_review`, `qa_fail_retries_implementer_then_passes`, `qa_limit_exceeded_rolls_back`, and `resume_from_phase_qa`.

## Files to Modify/Create
- `src/workflow/parser.rs` - add `QaDecision`, QA parser, and parser tests.
- `src/prompts/templates.rs` - add `default_qa_template()` and QA output contract text.
- `src/cli/init.rs` - write `templates/qa.md` during workspace initialization.
- `src/workflow/orchestrator.rs` - implement QA transitions, QA phase execution, QA feedback loop, limit handling, QA prompt construction, parse-retry format mapping, and dry-run/tmux QA updates.
- `tests/orchestrator.rs` - add end-to-end QA phase transition/loop tests.
- `tests/init_command.rs` - assert init creates QA template file.

## Dependencies
- Requires: QA Schema and Config Plumbing (Loop 1)
- Blocks: QA Acceptance Gate in Completion Phase; Planner acceptance-failure context injection; QA result UX/reporting polish
