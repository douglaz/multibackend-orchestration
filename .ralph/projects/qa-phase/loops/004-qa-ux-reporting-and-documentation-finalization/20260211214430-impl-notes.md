# Implementation Notes

## Decisions Made
- **QA summary in `status.rs` uses section-based extraction**: The `extract_section_lines()` function looks for `## Verification Summary` (pass) or `## Failures` (fail) in the QA artifact body, matching the QA parser contracts from Loops 1-2. Falls back gracefully to "(no summary available)" when sections are missing or the artifact file cannot be read.
- **Up to 3 summary lines**: Consistent with the existing `extract_required_change_lines()` pattern for review feedback, QA summary extraction caps at 3 lines to keep status output concise.
- **History verbose QA line format**: `QA: N attempts, last=verdict, report=path` — the report path is only shown when attempts > 0, keeping the zero-attempts case clean (`QA: 0 attempts, last=none`).
- **Non-verbose and JSON history unchanged**: Non-verbose output format (`Loop N: name (status)`) is untouched. JSON output uses `serde_json::to_value()` on the existing `FeatureLoopState` struct, which already includes `qa_results` via `#[serde(default)]` from Loop 1.
- **Unit tests in `status.rs` module**: Since `status.rs` is a private module (`mod status;`), the extraction helper tests are placed in an in-module `#[cfg(test)]` block for direct access to `extract_section_lines`, `extract_required_change_lines`, and `strip_frontmatter`.
- **Integration tests in `tests/status_history.rs`**: Cover QA data structure access patterns used by both status and history rendering — zero attempts, pass, fail, multi-attempt sequences, non-verbose output stability, JSON serialization backward compatibility, and legacy state deserialization.
- **PLAN.md documentation is comprehensive**: Added QA to workflow diagram, state machine, artifact tables, parser contracts, role table, model defaults, config keys (global + project), CLI flags, directory structure, and error table.
