# Implementation Notes

## Decisions Made
- Extended the `mark_project_failed` trigger in `src/cli/run.rs` to include `QaIterationLimitExceeded` and `ReviewIterationLimitExceeded` error variants alongside the existing `BackendTimeoutExhausted`, using a single `matches!` expression with `|` alternation — this is the minimal change needed to satisfy the failure-marking acceptance criterion while preserving the existing pattern.
- Renamed `qa::iteration_limit_rolls_back` → `qa::iteration_limit_fails` and `run::review_limit_rollback` → `run::review_limit_fails` to reflect the explicit failure semantics, while keeping all existing setup paths (mock scripts, config values) intact.
- Added `assert_json_field(&state, "status", &json!("failed"))` to both hardened rollback tests, which validates the new `mark_project_failed` behavior.
- Added `assert_git_tag_not_exists` to the review-limit test (the QA test already had it).
- Created `review_feedback_once_then_approve_script` as a new mock script in `mock_scripts.rs` that uses a counter file to reject on the first review iteration and approve on the second, producing exactly one review-feedback cycle and a `*-impl-response-001.md` artifact.
- The `impl_response_artifact_on_review_feedback` test uses the existing `list_artifacts` + suffix filter pattern rather than adding a new assertion helper, keeping the change minimal and consistent with existing test patterns (e.g., `artifact_naming` test).
- No changes to `src/validate/assertions.rs` were needed — existing helpers (`parse_yaml_frontmatter`, `assert_git_tag_not_exists`, `assert_no_loop_artifacts`, `assert_json_field`) were sufficient for all new assertions.

These helpers were not needed — `assert_no_loop_artifacts` already exists, and artifact suffix matching is done inline via iterator filter, consistent with existing patterns.
