# Implementation Notes

## Decisions Made
- Used `tokio::task::block_in_place` + `Handle::current().block_on()` instead of bare `Handle::block_on()` for the async backend execution bridge. The spec suggested `Handle::current().block_on()` alone, but this panics when called from within a tokio task context (which the daemon dispatch code runs in). `block_in_place` signals the tokio scheduler that the current thread will block, making it safe to then call `block_on()`.
- Hardcoded the refinement system prompt as a constant in `refine.rs` rather than loading from a template file. This follows the spec's guidance that it's a daemon-internal concern, not user-facing.
- Set `MIN_OUTPUT_LENGTH = 20` for refinement output validation, matching the spec's threshold.
- Existing daemon conformance tests that assert exact raw idea pass-through (`runtime_adopt_pending_fetches_raw_idea_and_uses_idea_flag`, `runtime_adopt_pending_fetch_failure_uses_metadata_fallback`) were updated to disable refinement, since refinement is enabled by default and would transform the idea before passing to the child. These tests focus on raw idea hydration, not refinement.
- The `post_idempotent_comment` call for the "refined-prompt" phase is placed between refinement and spawn in `dispatch_task`, with errors caught and logged as warnings, never aborting dispatch.
- No new mock scripts were added to `mock_scripts.rs`. The conformance tests create inline mock scripts specific to their refinement scenarios, keeping them self-contained.

## Spec Deviations
- The spec suggested `tokio::runtime::Handle::current().block_on(...)` directly, but this causes a panic ("Cannot start a runtime from within a runtime") because the daemon dispatch runs inside a tokio task. Changed to `tokio::task::block_in_place(|| Handle::current().block_on(...))` which is the correct pattern for blocking sync code within a multi-threaded tokio runtime.
- No changes were made to `mock_scripts.rs` — the new conformance tests use inline mock scripts written via `h.write_mock_script()` since each test needs a unique mock setup (logging, specific behaviors). This keeps tests self-contained and avoids adding complexity to the shared mock module.
