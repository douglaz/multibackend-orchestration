# Feature: Decouple Log Writes from Timeout Paths and Strengthen Review Retry Test

## Description
Address two accepted final-review amendments: (1) AMEND-PRD-LOG-001 — move debug log file persistence out of timeout/deadline-critical execution paths so filesystem I/O cannot consume backend budget, and (2) AMEND-TEST-002 — strengthen the `review_retry_callback_captures_malformed_attempts` conformance test to validate structured log-entry fields (`raw_output`, `error`, `validation.status`) and exercise the production callback wiring in `run_review_with_retry_sync` rather than manually re-implementing it in test code.

## Acceptance Criteria
- [ ] In `run_review_with_retry_sync`, the `on_attempt` callback inside the `tokio::time::timeout` block only collects events in memory (no `logger.log_attempt()` calls inside the timeout).
- [ ] After timeout resolution in `run_review_with_retry_sync`, all collected attempt events are persisted to disk via `logger.log_attempt()`.
- [ ] In `run_backend_sync`, log persistence is performed after the `tokio::time::timeout` block returns, not inside it. The `remaining` time calculation and timeout wrapping exclude log-write time.
- [ ] Best-effort semantics preserved: any log-write failure emits `eprintln!` and continues; no panics or error propagation from logging.
- [ ] Existing workflow behavior (retry counts, decisions, transitions, return values) remains unchanged.
- [ ] The `review_retry_callback_captures_malformed_attempts` test reads and parses each log file's JSON content, asserting: `raw_output` is populated (not null), `error` is null, and `validation.status` equals `"review_parse_failed"`.
- [ ] The test exercises the production callback wiring by calling `run_review_with_retry_sync` (or the equivalent production path that includes logger construction and the callback) rather than manually calling `logger.log_attempt()` in test code.
- [ ] All existing tests continue to pass (`cargo test`, `cargo check`, `nix build`, `ralph validate`).
