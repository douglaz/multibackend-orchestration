# Feature: Feature-loop backend re-resolution on resume

## Description
Ensure that the three feature-loop phases (`Implementing`, `QA`, `Reviewing`) always resolve effective backends from current config via `assign_feature_backends(...)`, instead of conditionally falling back to reconstructed `loop_state.backends.*` values. Remove the `is_backend_available()` gating that currently guards recalculation. Reconstructed backend fields remain intact for provenance and drift comparison only. Add consistent drift logging with `role`, `loop_number`, `original`, and `resolved` fields when mismatches are detected. Introduce the `is_resumed_state: bool` flag in orchestrator `run()` — initialized to `true` after state reconstruction and set to `false` after the first outer-loop iteration completes — so that subsequent features (completing-phase gating) can use it.

## Acceptance Criteria
- [ ] In `Phase::Implementing`, the effective implementer backend is always resolved via `assign_feature_backends(...)` regardless of whether the reconstructed backend is available.
- [ ] In `Phase::QA`, the effective QA backend is always resolved via `assign_feature_backends(...)` regardless of whether the reconstructed backend is available.
- [ ] In `Phase::Reviewing`, the effective reviewer backend is always resolved via `assign_feature_backends(...)` regardless of whether the reconstructed backend is available.
- [ ] The `is_backend_available()` check is removed from the `Implementing`, `QA`, and `Reviewing` phase resume paths.
- [ ] Reconstructed `loop_state.backends.*` values are not used as execution source of truth in these three phases; they are used only for drift comparison.
- [ ] `FeatureLoopBackends` struct reconstruction remains unchanged (provenance/audit preserved).
- [ ] An `is_resumed_state: bool` local is introduced in `run()`, initialized to `true` immediately after state reconstruction.
- [ ] `is_resumed_state` is set to `false` after the first outer-loop iteration completes (after `completed_feature_loops` increments).
- [ ] On each mismatch between reconstructed and re-resolved backend values, a `warn!` is emitted with fields: `role`, `loop_number`, `original`, `resolved`.
- [ ] No drift warning is emitted when reconstructed and re-resolved values match.
- [ ] No changes to `state.json` schema, `register_feature_loop`, or backend struct schemas.
