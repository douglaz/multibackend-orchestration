# Feature: Completion/final-review backend re-resolution on resume

## Description
Loop 1 completed feature-loop (`Implementing`/`QA`/`Reviewing`) re-resolution and introduced `is_resumed_state`.  
This feature closes the remaining resume gaps in `Completing` and `FinalReview`: execution must always use config-resolved completion planner logic, re-resolve completer panel only on true resume entry, and stop using reconstructed completion backends as execution source of truth (provenance only).

## Acceptance Criteria
- [ ] In `Phase::Completing`, resolve effective completion planner each entry via `assign_completion_backends(...)` (for loop parity), and use that resolved planner for completion-phase execution context.
- [ ] `Phase::Completing` does not use `completion.backends.planner` as execution source of truth; reconstructed planner is used only for drift comparison/logging.
- [ ] If reconstructed planner differs from resolved planner, emit `warn!` with `role`, `loop_number`, `original`, and `resolved`; emit no warning when equal.
- [ ] In `Phase::Completing`, completer panel re-resolution via `resolve_completion_panel(...)` happens only when `is_resumed_state == true`.
- [ ] In resume completion entry (`is_resumed_state == true`), completers are resolved from current config and used for execution.
- [ ] In same-run completion entry (`is_resumed_state == false`), use `completion.backends.completers` as already resolved in-process; do not re-resolve panel and do not perform extra health-check gating.
- [ ] Completer-panel drift warning is emitted only when reconstructed completer list is non-empty and differs from resume-resolved panel, with fields `role`, `loop_number`, `original`, `resolved`.
- [ ] Existing empty-panel fallback behavior in `Phase::Completing` is removed (no new empty fallback logic added).
- [ ] `Phase::FinalReview` resolves planner at the phase call site using `assign_completion_backends(...)` and passes it into `run_final_review_phase(..., planner_backend: &str)`.
- [ ] `run_final_review_phase` no longer reads `completion.backends.planner` for execution decisions; it uses the passed `planner_backend`.
- [ ] Failure invariants: if planner/panel re-resolution fails before completer/final-review execution, phase remains `Completing`/`FinalReview` respectively, no verdict/progress artifact is written for that step, and provenance fields in reconstructed state remain unchanged.
- [ ] `state.json` schema, completion/backend structs, quick-dev orchestrator behavior, and session reconstruction defaults remain unchanged.
