# Implementation Notes

## Decisions Made
- **Completing planner re-resolution**: Resolved effective planner via `assign_completion_backends(...)` on every entry to `Phase::Completing`, matching the feature-loop pattern from Loop 1. The reconstructed `completion.backends.planner` is only used for drift comparison.
- **Completer panel resume-gating**: Used the existing `is_resumed_state` flag to gate completer panel re-resolution. On `is_resumed_state == true`, completers are re-resolved from config via `resolve_completion_panel(...)`. On `is_resumed_state == false` (same-run entry), the in-process `completion.backends.completers` are used directly without health-check overhead.
- **Removed empty-panel fallback**: The old code had a special case that re-resolved completers when the reconstructed list was empty. This was replaced by the broader resume-gating logic — on resume, completers are always re-resolved (covering the empty case); on same-run, they're already valid.
- **FinalReview planner injection**: Moved planner resolution to the `Phase::FinalReview` call site in the main loop, passing the resolved planner as `planner_backend: &str` into `run_final_review_phase`. The function no longer reads `completion.backends.planner`.
- **Drift logging**: Used the existing `log_backend_drift_if_mismatch` for planner drift (single string comparison). For completer panel drift, used a direct `warn!` with `role="completer"` and `?` debug formatting for the Vec lists, only when reconstructed list is non-empty and differs.
- **Failure invariants**: If `assign_completion_backends` or `resolve_completion_panel` fails, the `?` propagation means the phase remains unchanged (Completing/FinalReview) and no verdict/progress artifact is written.

## Spec Deviations
- The completer panel drift warning uses `original = ?reconstructed_completers` and `resolved = ?resolved_panel` (Debug-formatted Vec), which differs from the single-string `original = %original` format used by `log_backend_drift_if_mismatch`. This is necessary because the panel is a `Vec<String>`, not a single string. The message text and field names are consistent with the spec requirement.

## Testing
- Added 4 new conformance test cases in `src/validate/tests_resume_backend_resolution.rs`:
  1. `completion_planner_drift_on_resume` — verifies planner drift warning when `starting_backend` changes between runs while state is in Completing phase
  2. `completion_completer_panel_drift_on_resume` — verifies completer panel drift warning when `completion_backends` config changes between runs
  3. `final_review_planner_drift_on_resume` — verifies planner drift warning when state is in FinalReview phase and `starting_backend` changes
  4. `same_run_completion_no_panel_reresolution` — verifies no completer panel drift warning when completion is entered within the same run (not a resume)
- All tests registered in the existing `tests()` function, no changes to `src/validate/mod.rs` needed (module was already registered in Loop 1)
