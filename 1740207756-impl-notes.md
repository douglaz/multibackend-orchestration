# Implementation Notes

## Decisions Made
- **Draft-boundary filtering via comment ID comparison**: The `find_new_feedback_comments` function now takes a 4th parameter `latest_draft_comment_id: Option<u64>`. The effective boundary is `max(last_processed_comment_id, latest_draft_comment_id)`, ensuring pre-draft comments are always excluded even if they were previously unprocessed. This is simpler and more robust than timestamp-based filtering since comment IDs are monotonically increasing.
- **Marker timestamp hydration before posting**: In `do_pending_to_awaiting`, the code now checks `find_comment_with_marker` before calling `post_comment_with_marker`. If the marker already exists (restart scenario), `questions_posted_at` is set from the existing comment's `created_at` rather than `Utc::now()`. This avoids the edge case where valid user answers posted between the original question time and the daemon restart would be skipped.
- **No changes to github.rs**: The existing `find_comment_with_marker` already returns `IssueComment` with `id` and `created_at` fields, which is sufficient for the hydration logic. No new helpers or structural changes were needed in `github.rs`.
- **Transition-path unit tests use pure functions**: The unit tests verify the decision paths (pending pickup, answer selection, approval detection, revision path, retry exhaustion, pre-draft exclusion) by testing the internal helper functions directly rather than requiring mock GitHub interactions.

## Spec Deviations
- **github.rs changes minimal**: The spec suggested extending marker comment helpers to return structured metadata. The existing `find_comment_with_marker` already returns `IssueComment` with all needed fields (`id`, `created_at`), so no structural extension was needed. The hydration logic was implemented entirely in `interactive_prd.rs`.
- **Draft-boundary uses ID comparison, not timestamp**: The spec mentions "draft timestamp" for boundary filtering. Since GitHub comment IDs are monotonically increasing and we already use ID-based cursor tracking everywhere, the implementation uses `latest_draft_comment_id` as the boundary rather than introducing a separate timestamp field. This is more consistent with the existing cursor semantics.
