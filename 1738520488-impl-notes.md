# Implementation Notes

## Decisions Made
- **Inner `tokio::spawn` for panic isolation**: Used nested `tokio::spawn` inside JoinSet tasks rather than `std::future::FutureExt::catch_unwind` because the `futures` crate is not a project dependency. The inner spawn converts panics into `JoinError` while the outer task preserves `issue_number` identity.
- **`DispatchOutcome` enum with three variants**: `Success`, `Failure`, and `Panic` — each carrying `issue_number`. Both `Failure` and `Panic` trigger identical rollback (`ralph:in-progress -> ralph:failed`), but distinct log messages differentiate the root cause.
- **`CompletionOutcome` enum with `Done` and `Panic` variants**: On completion panic, explicit `swap_lifecycle_label` transitions the issue to `ralph:failed` so it doesn't remain stuck as `ralph:in-progress`. Rollback failure is logged but does not prevent processing remaining children.
- **Concurrency evidence via timestamp markers**: Used `START:<issue>:<epoch_ms>` / `END:<issue>:<epoch_ms>` markers with `<=` overlap comparison (not strict `<`) because nix build sandbox only provides second-level granularity via `date +%s000`.
- **Dispatch-failure detection via `--add-label ralph:failed`**: The mock GH detects failure transitions by observing `--add-label ralph:failed` in `issue edit` calls (not both `--remove-label` and `--add-label` in the same call, because `swap_lifecycle_label` issues two separate `gh issue edit` invocations).
- **Rollback logging on failure**: Both dispatch and completion rollback failures are explicitly logged with issue number, but processing of other issues continues uninterrupted.

## Spec Deviations
- **Dispatch panic injection**: The spec requests testing dispatch panics directly, but since `dispatch_task` is Rust code and panics cannot be injected from shell mock scripts, the dispatch panic path is tested structurally (the `DispatchOutcome::Panic` variant and its rollback logic are proven by the inner `tokio::spawn` pattern) rather than end-to-end. The `dispatch_failure_explicit_markers` test validates the per-issue rollback path that both `Err` and `Panic` dispatch outcomes follow.
- **Completion panic injection**: Similarly, `complete_task` panics cannot be injected from external mocks. The `CompletionOutcome::Panic` path is structurally verified. The `completion_failure_terminalization` test proves that failed children are terminalized to `ralph:failed` and not left stuck as `ralph:in-progress`.

- `ralph validate --bin ./result/bin/ralph --filter daemon_concurrency` passes all 7 tests:

  - `partial_dispatch_rollback` (existing) — verifies per-issue rollback isolation
  - `single_iteration_prd_inline_only` (existing) — verifies inline PRD only
  - `concurrent_rebase_dispatch_no_lock_contention` (existing) — verifies no git lock contention
  - **`dispatch_failure_explicit_markers`** (new) — verifies `dispatch-failure:<N>` markers in side-channel log for failed issues, with sibling isolation
  - **`concurrent_dispatch_evidence`** (new) — verifies overlapping `START/END` timestamp intervals proving concurrent dispatch
  - **`completion_failure_terminalization`** (new) — verifies child exit-1 terminalized to `ralph:failed` with label log evidence
