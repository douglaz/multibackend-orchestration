# Implementation Notes

## Decisions Made
- **Bot-login resolution moved inside transition wrappers**: Instead of calling `get_or_fetch_bot_login()` in `advance_prd_issue()` where the `?` operator would bypass `finish_transition()`, the bot-login resolution is now performed inside `transition_awaiting_answers_to_awaiting_feedback()` and `transition_awaiting_feedback()` using `.and_then()` chaining. This routes bot-login errors through `finish_transition()` → `apply_transition_result()`, ensuring `error_count` increments on each tick and `Failed` state is reached after 3 consecutive failures.
- **Transition wrapper signatures changed from `&str` to `&mut Option<String>`**: Both `transition_awaiting_answers_to_awaiting_feedback` and `transition_awaiting_feedback` now accept `bot_login_cache: &mut Option<String>` instead of a pre-resolved `bot_login: &str`. The cache semantics are preserved: successful lookups are cached within a tick; failures leave the cache empty so the next tick retries.
- **Approval label order reversed to boundary-safe**: Changed from remove-active-then-add-done to add-done-then-remove-active. This ensures that on partial failure (add-done fails), `ralph:prd-active` is still present so the issue remains poll-visible for retry. If add-done succeeds but remove-active fails, the issue has both labels but `Done` is not persisted (the error propagates), so the next tick can retry the remove.
- **No changes to `do_approval_transition` state mutation**: The `state.state = PrdWorkflowState::Done` assignment already occurs after both label operations succeed, so partial label failure naturally prevents `Done` from being persisted. The approval comment uses `post_comment_with_marker` which is idempotent via marker detection, preventing duplicate status comments across retries.

## Spec Deviations
- None. All acceptance criteria are implemented as specified.
